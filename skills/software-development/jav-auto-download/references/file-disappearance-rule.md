# 文件「消失」不要追查、不要重下

## 结论（用户 2026-10-31 明确规则）

> 「只要下好了就不会丢，没了就是我把文件移走或者删除了，所以以后只要确认下载完成后，就不用再管」

**下载 — 校验 — 结束。** 校验通过（字节比对 + ffprobe + 字幕配对）就算这条交付完成。
此后 `/opt/data/PikPak/Inbox-JAV/` 里同名文件不见了，一律按「用户自己移走或删除」处理：
不追查、不重新离线、不重新拉回、不装监视器。用户想恢复会自己说番号。

## 踩过的坑（别再重复）

2026-10-31 一天内 8 个番号 mp4 陆续从目录消失，我误判为「有东西在删文件」并做了一串
错误的排查与自动化，全部无效而且有害：

1. **怀疑 cron / 插件 / 守护脚本删文件** — 全盘查 disk-cleanup 追踪清单、cron 执行记录、
   挂载点、sync 脚本、`/proc` fd 持有者，全部无果。`disk-cleanup` 插件只清缓存和封锁脚本，
   不碰视频；cron 里只有 OCR 补入库任务。
2. **怀疑 rclone 自己删** — 监视器把「当时唯一持有该目录 fd 的进程」记成嫌疑，正好是
   正在下载的 rclone，看起来像铁证，其实是伪相关。`pikpak` 远程是 WebDAV，`rclone copy`
   碰不到本地文件。
3. **怀疑 FUSE 写回层丢数据** — 编了一整套「`zfuse.zfsv3` 在 15 线程 × 32M buffer 下丢
   extents」的机制解释，还据此改了并发、加 `os.sync()`、加 20 秒观察窗。真因是用户在
   自己搬文件，这套机制解释纯属脑补。
4. **加了监视器和自动巡检重下** — 监视器每 2 秒轮询记录「删除」，巡检发现缺失就自动重拉，
   结果把用户已经搬走的文件又拉回来一份，白烧带宽，还跟他抢目录。最终全部拆掉。

## 教训

- **用户自己会动文件。** 目录里少文件，先假设是用户操作，别假设是故障。
- **只有「唯一持有 fd 的进程」这种证据不算证据**，相关性不等于因果。
- **不要为了一个没确认的故障去加自动化。** 自动化一旦和用户的手工操作打架，损失比故障本身大。
- 校验通过就撒手；用户要恢复会明说番号，届时单独补，不动整批。
