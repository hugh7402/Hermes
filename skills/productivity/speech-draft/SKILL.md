# 发言稿撰写（政务/央企场合，口头汇报）

## 何时用

- 座谈会发言、汇报发言、总结汇报讲演稿、表态发言、领导讲话稿
- 带**硬性时长限制**（"每家汇报不超过 5 分钟"）的口头材料
- 会议方案里指定了段落结构（如"一是谈收获体会，二是谈取得成果，三是谈下一步思路举措"）

与 `plan-writer` 的区别：plan-writer 写**书面**方案/报告/建议书（长文、可展开）；本 skill 写**要念出来**的稿子（时间盒、口语化、段落字数硬约束）。

---

## 🚨 用户硬规则（2026-09-18 老博会发言稿实战教训）

### 1. 先算字数预算，再动笔

**中文口播 ≈ 230 字/分钟**（慢 200 / 快 260）。

| 时限 | 目标字数 |
|---|---|
| 3 分钟 | 700 |
| 5 分钟 | **1100-1200** |
| 8 分钟 | 1850 |
| 10 分钟 | 2300 |

血泪教训：这一篇**迭代了 6 轮**（1350 → 1229 → 1469 → 1315 → 1189 → 1243 → 1479 → 1356 → 1203 → 1279 → 1210 字），每一轮都是"写完才发现超时"。**第一稿就按目标字数写**，不要写完再砍。生成后必须用脚本打印字数 + 预计时长（见 `scripts/gen_speech_docx.py`）。

### 2. 内容按用户给的提纲落地，不要自己另起框架

用户原话：「**我的意见是按照这几个方面说一下**：一是…二是…三是…」——逐条 1:1 落地成段落，并**保留他的原话措辞**（案例中必须保留的："集约、灵活"、"一地创新、全省复用"、"化解系统割裂"、"详细调研/架构优化/模式转变"）。用户列了三条就写三条，不要自作聪明扩成五条、也不要合并。

### 3. 术语用用户的**一手材料**，绝不用公开检索到的历史表述

用户纠正原话：「**应该没有"1367"之类的了**」。我从公开报道里抄的"1367（一生有期）"架构 + "惠秦养/温秦助/护秦童"三大品牌是**旧版**，现行表述是"**一网通用、二期应用、保障体系**"。

做法：
- 把用户发来的**全部材料**读完：会议方案 PDF、展项配置表、现场照片、上期文稿
- **照片必须 `vision_analyze` 逐字读**——缩略图描述会漏掉架构图上的层级文字（"一网通用/二期应用/保障体系"就是这么读出来的，缩略图只给了一句概括）
- 检索结果只用来补**背景/外部事实**（会议规模、主办方、政策文件），涉及用户本单位/本项目的名称、架构、系统清单、数据，一律以一手材料为准

### 4. 缺数据用 `【待填】` 占位，绝不编数字

写完明确列出待填项让用户补（例：接待人次、领导视察、合作意向数、需求条数）。用户对这种处理方式是认可的；编造数字是红线。

### 5. 政府场合分寸

- 以"我代表 X 单位"开口，不写"我觉得"
- 讲成效**见事见数**：具体数字（914 万老年人、13 个业务系统）+ 具体系统名 + 具体设备/人员配置
- 结尾表态收束："将一如既往…全力配合…" + "汇报完毕，谢谢大家！"

## 标准流程

```
① 通读全部材料（会议方案 PDF 定时间/时长/参会人/议程 + 用户一手材料）
② 确认提纲（用户给了照办；没给就先给框架让用户确认）
③ 算字数预算：总额 = 时限×230，按段落分配（开场 5% / 主体三段各 30% / 结尾 5%）
④ 写稿（口语化，能念出来，长句拆短）
⑤ 脚本统计字数 + 分段字数 + 预计时长，超了按段落比例砍
⑥ 生成公文格式 docx + docx_validate 校验 + 微信交付
⑦ 消息里贴全文 + 列待填项 + 给"讲得慢可删哪段"的现场预案
```

### 段落预算示例（5 分钟 = 1150 字）

| 段落 | 字数 | 作用 |
|---|---|---|
| 开场 | 50 | 称呼 + 感谢 + 一句"围绕 X、Y、Z 作简要汇报" |
| 一、收获体会 | 380-420 | 看到什么 → 与本单位的关联 → 与上位规划的衔接 |
| 二、取得成果 | 350-380 | 具体做法（带一手数字）+ 成效 + 可借鉴经验 |
| 三、下一步 | 280-310 | 2-4 条"一是…二是…"，每条=可检验的动作 |
| 结尾 | 60 | 表态 + "汇报完毕，谢谢大家！" |

## 内容质量诀窍（用户要"有洞察"，不要套话）

**收获体会不要写"收获很大、很受启发"**——写"具体观察 + 关联分析"。案例范本：

> 展会上的信息化产品大致分布在六个领域：智能适老装备、智慧养老平台、医养康养服务、适老化改造、养老金融保险、旅居康养。**但共同特点很突出——大多是单点设备、单机构系统，跨部门、跨机构的数据贯通能力弱。**
>
> 展会上的产品是"**点**"，智慧民政要做的是把点连成"**线**"和"**面**"。

**成果段要有一手数字**：系统数量、设备构成（8 台电视 = 主大屏 1 + 业务分屏 6 + 创新成果展播 1，比笼统"8 台电视"专业）、人员配置（讲解 4 + 运维 1）、接待量、达成意向数。

**下一步每条要有可检验的动作**："逐项摸排各地市现有系统建设情况、数据接口和业务流程" ✅ / "加强、推进、深化" ❌（空动词打头是大忌）。

**给关联分析找落点**：把"我们看到的东西"接到"我们的现有成果"再接到"上位规划的条款"（如"十五五"规划的"五床联动""开门办院""两院共建"、高龄补贴"免申即享"、旅居养老试点），并点出"这些任务的共同点是跨机构、跨部门协同，必须有一体化数据底座"。

## 公文格式 docx（用户项目统一格式）

| 元素 | 规格 |
|---|---|
| 标题 | 方正小标宋简体 **22pt** 加粗居中（两行用 `\n` 拆行） |
| 副标题（单位/日期） | 楷体 **15pt** 居中 |
| 正文 | 仿宋 **16pt**（三号），**首行缩进 32pt（=2 字符）**，行距 **1.5** |
| 小标题（一、二、三） | 黑体 16pt，首行缩进同上 |
| 页面 | A4；页边距 上 3.7 / 下 3.5 / 左 2.8 / 右 2.6 cm |

直接跑 **`scripts/gen_speech_docx.py`**（改文件顶部的 TITLE / SUB / DATE / BODY 四个变量即可，脚本自带字数与时长统计），生成后跑 `docx_validate.py` 确认 `ok: true`。

⚠️ **本机无 soffice/libreoffice → 不能转 PDF**。用户若要 PDF 要如实说明，不要假装能转。

## 交付前校验清单

- [ ] 字数 ≤ 时限 × 230？分段字数是否均衡（没有某段吃掉全部预算）？
- [ ] 用户给的提纲条目是否 1:1 落地？他的原话措辞是否保留？
- [ ] 文中所有专有名词/架构名/系统名/数字，是否**每一个**都能追溯到用户的一手材料？
- [ ] 缺口是否用 `【待填】` 标注，并在回复里逐条列给用户？
- [ ] docx 格式与项目模板一致？`docx_validate.py` 返回 `ok: true`？
- [ ] 是否给了"讲得慢时可删哪一段"的现场预案（并说明删掉后结构不受影响）？
- [ ] 是否在消息里贴了**全文**（用户要在手机上直接看/改，只给文件不够）？

## 踩坑记录

- **字数估计不能凭感觉**：连续 5 次目测都偏低（写完都超时 1 分钟以上）。用脚本统计。每加一句细节（约 30-50 字）就会吃掉预算，**改完必须重新统计**。
- **多轮迭代时不要只改局部**：字数超了要按段落比例砍，不要只砍结尾（结尾本来就短，砍了没用还伤结构）。
- **照片别只看缩略图描述**：缩略图给的是概括（"三阶段应用架构 + 六要素保障体系"），逐字读才能拿到"一网通用 / 二期应用 / 保障体系"和下面挂的具体条目。
- **公开检索 ≠ 项目事实**：检索到的平台架构、口号、系统清单往往是旧版或媒体简化版；用户项目的一手材料（方案 PDF / 配置表 / 现场照片）才是准的。写错一次就被纠正。
- **会议方案 PDF 要读全**：时间、地点、参会人范围、议程顺序、时长限制、发言顺序都在里面——"每家不超过 5 分钟"这种硬约束漏读会导致整篇白写。
- **环境坑**：本机生成脚本走 `cd /opt/data/.tmp_tests && export PATH=/opt/data/.venv/bin:$PATH && python3 <裸名>.py`（绝对路径直调 .py 会崩）；`python-docx` 已装 1.2.0。
