# 会议纪要（中文）

用户把会议录音/视频丢过来，产出可直接入库的 Obsidian 纪要。

## When to Use / 触发场景

- 「这是会议录音，整理成纪要」
- 微信直接发来 mp3/m4a/amr/wav 等音频或会议视频
- 「把这个录音转成文字」

不适用于：只有文字笔记要做成任务清单 → 用 `meeting-action-items`。

## 铁律

1. **不许编**。转写里没有的人名、数字、时限、结论一律不写。听不清的写 `【听不清】`，没提到的字段留空。
2. **不许把提议当决策**。会上只是「可以考虑」「回头看看」的，放进「待定」不放「关键决策」。
3. **不许编发言人身份**。ASR 只给「说话人1/2」时不猜他是不是厅长、处长、某某总。
   会议通知截图（会议名称/时间/地点/主持人/参会领导/计划人数）**只用来填表头**；
   通知上的人名不得当作正文发言人或参会名单写进纪要——通知只说明「应该来」，
   不等于「来了、讲了」。要写发言人名字，唯一依据是转写里能明确对上说话人。
4. **保密优先**。会议录音可能涉密，**只准用境内服务**（百炼）。禁止把音频送给 Google/Gemini 等境外 API。

## ASR 通道

### 实测横评（2026-11，212 字中文政务文本 / 17 个专有名词 / 每个模型跑 3 次）

| 模型 | 调用方式 | 相似度 | 最差 | 专名 | 耗时 | 稳定 | 结论 |
|---|---|---|---|---|---|---|---|
| **`qwen3.8-omni-flash`** | OpenAI 兼容 | **1.0000** | 1.0000 | **17/17** | 4.4s | ✅ | ✅ **默认用这个** |
| `qwen3.5-omni-flash` | OpenAI 兼容 | 0.9991 | 0.9974 | 17/17 | 0.9s | ⚠️ 会飘 | 备选 |
| `qwen3-asr-flash` | OpenAI 兼容 | 0.9896 | 0.9896 | 15/17 | 1.3s | ✅ | 快，但「秦务员」常错 |
| `fun-asr-flash-2026-06-15` + 热词 | 顶层 `format`+`vocabulary` | 0.9819 | 0.9819 | 16/17 | 1.9s | ✅ | 快且可加热词，次选 |
| `fun-asr-flash-2026-06-15` 无热词 | 顶层 `format` | 0.9699 | 0.9664 | 14/17 | 2.2s | ⚠️ | 不要单独用 |
| `fun-asr` / `qwen3-asr-flash-filetrans` | 异步 HTTP | — | — | — | — | — | ❌ 只认公网 HTTPS，`oss://` 报 `REQUEST_INVALID_FILE_URL_VALUE` |
| `qwen-audio-3.0-asr-flash` | OpenAI 兼容 | — | — | — | — | — | ❌ 试过四种格式均报 `format is empty`，用不了 |

**结论：固定用 `qwen3.8-omni-flash`。** 它是唯一 3 次全对且零波动的。
62 分钟会议约 9 分钟转完、不到一毛钱。

**模型换代或额度开关变动后，跑 `scripts/asr_bench.py` 重测，不要手写测试。**
默认用内置政务文本合成音频（天然有标准答案），跑 3 次看稳定性；
要贴近实战就 `--audio <真会议片段> --ref <标准答案.txt>`。
**判据是先看「最差一次」而不是平均值**——生成式单次全对不代表可靠，
`qwen3.5-omni-flash` 就出现过一次 0.9974 的抖动，平均值看不出来。

热词确实有效（`fun-asr-flash` 加顶层 `vocabulary` 后命中 14→16、相似 0.9699→0.9819），
但加上热词仍不如 omni 不加。所以**正规会议录音优先 omni**；确实需要快时用
`fun-asr-flash` + 顶层热词。

### 三个容易踩的格式坑

调用结构各不相同，搞错就是 `format is empty` 或 `UNSUPPORTED_FORMAT`：

```python
# ① omni 类：data URI + input_audio.format
{'model': 'qwen3.8-omni-flash', 'modalities': ['text'], 'stream': False,
 'messages': [{'role': 'user', 'content': [
     {'type': 'text', 'text': prompt},
     {'type': 'input_audio', 'input_audio': {'data': f'data:audio/mpeg;base64,{b64}', 'format': 'mp3'}}]}]}

# ② qwen3-asr-flash：data URI，但绝对不要带 format 字段
{'model': 'qwen3-asr-flash', 'stream': False,
 'messages': [{'role': 'user', 'content': [
     {'type': 'input_audio', 'input_audio': {'data': f'data:audio/mpeg;base64,{b64}'}}]}]}

# ③ fun-asr-flash：format 和 vocabulary 都放请求顶层，data 用 data URI 且 input_audio 里不带 format
{'model': 'fun-asr-flash-2026-06-15', 'stream': False, 'format': 'mp3',
 'vocabulary': {'秦务员': 4, '民政通': 4},
 'messages': [{'role': 'user', 'content': [
     {'type': 'input_audio', 'input_audio': {'data': f'data:audio/mpeg;base64,{b64}'}}]}]}
```

热词权重 1-5，推荐 4，过高会拖累其他词。放在 `asr_options.vocabulary` 里**不生效**，必须放顶层。

### 排查顺序

报 `AllocationQuota.FreeTierOnly` 时，先用 `qwen-plus` 探一下账号付费能力：
它能正常返回 token 用量，就说明账号没欠费、没认证问题，是那一个模型自己的开关，
**直接换模型即可，不要让用户去翻控制台**（曾让用户白查半天，实际是模型级开关）。

```bash
/opt/data/.venv/bin/python3 scripts/transcribe_omni.py "$AUDIO" \
  --out /tmp/transcript.json --chunk 600 \
  --terms "专有名词1,专有名词2,..."
```

- 默认切 600 秒。62 分钟音频 → 7 段 → 约 9 分钟跑完，不到一毛钱。
- **开跑前先确认 `--out` 目录可写。** 脚本现已自动 `makedirs`，但历史版本会**等全部段都转写完，
  才在最后一步 `FileNotFoundError`**——费用已扣、全文只在内存里、进程一退全没了，只能整个重跑。
  按 token 计费的批量作业，**任何落盘路径都要在第一次 API 调用之前验一遍**。
- **专有名词表必须传**：omni 不支持热词参数，只能写进 prompt，不传就会出现
  「秦务员→勤务员」这类同音错字。
- 空/碎片段（<1 秒）必须剔除，否则 API 报 `InvalidParameter: The audio is empty`。

### 🚨 重复循环检测（必做）

omni 是生成式模型，遇到嘈杂片段会陷入重复循环，输出几十遍
「这个时间，这个时间，这个时间……」或「一块九，一块九，一块九……」。

转写完**必须逐段扫一遍**：把每段按标点切句，统计最高频句占比和最长连续重复。
判据：**最高频句占比 >25% 或连续重复 ≥5 次 → 该段作废重跑**。

**句子数 <5 的短段不适用占比判据。** 一段只剩 2 句、79 字时占比天然是 50%，
纯属样本太小的误报（长录音末尾常有这种 20 秒碎片）。短段**只看连续重复次数**，
<5 次直接放过。判是否复读之前先数句子数。

重跑办法：只切出这一段，改为 150 秒小段重跑，prompt 里加一句
「绝对不要重复同一句话。听不清的地方留空，不要用重复的词填充」，
再对输出做连续重复句去重。

正常段的最高频句占比都在 3–6%（都是「对」「对吧」「啊」这类口语词），很好分辨。

## 流程

### 1. 拿到音频

微信发来的文件落在 `/opt/data/cache/documents/`。先确认：

```bash
ffprobe -v error -show_entries format=duration,size -of default=nw=1 "$F"
```

时长超 12 小时或 2GB 就先切分（`ffmpeg -f segment`）。

**只有直接发进本对话的文件才拿得到。** 用户说「录音发到微信快存了 / 文件传输助手 / 收藏」
时，那些是微信自己的云存储，扫 `cache/documents` 一定是空的。这时直接说「没到，
请直接发到这个对话框」，不要反复扫盘，也不要拿别处的旧文件顶替。

**例外：语音条转写失败时，网关会把音频落到本地并给出路径。** 消息形如
「voice message could not be transcribed automatically; the audio is available at: `<路径>`」——
那个路径是真实可读的 mp3（落在 `cache/documents/native-inputs/<hash>/` 下），
**立刻 `ffprobe` 量时长再转写**，别回一句「没收到」让用户重发一遍。
判据只有一条：**能把该文件列出、并量出时长就是拿到了**。快存/收藏拿不到是因为压根没有文件落到本地，
两者不是一回事，别混为一谈。

### 2. 转写

```bash
/opt/data/.venv/bin/python3 scripts/asr_bailian.py "$AUDIO" --out /tmp/asr.json --diarization
```

输出 JSON 含分段文本、时间戳、说话人（若开启）。
**转写失败不要瞎猜内容**，原样报告错误。

### 3. 生成纪要

用 DeepSeek 官方 `deepseek-chat`（非推理，快且够用）。先算清 token：
3 小时会议转写约 3-5 万字 ≈ 5-8 万 token 输入。分段喂，不要一次全塞。

按 `references/template.md` 的结构生成。**章节标题用原文，不要自创。**

**录音覆盖范围要如实标注。** 录音可能在汇报完、讨论刚开始时就断掉。纪要里
①在对应小节标题上注明（「讨论情况（录音至此结束）」），②文末写明录音时长与未录部分。
不要因为「纪要应当完整」就补写没录到的内容，也不要假装讨论环节已完整记录。
用户确认「录音就到这里」后，把已确认的口径写进「口径说明」并注明不再补录。

### 4. 元数据

- `tags`：10 个关键词，专有名词优先（系统名、机构名、项目名）
- `summary`：5 条，每条一句话，**结尾带 ` ×`**（用户笔记插件的标记）
- `related`：用 `[[ ]]` 链到相关笔记，找不到就留空数组，不要硬编

### 5. 入库

写进 `/opt/data/Obsidian Vault/Obsidian Vault/00-INBOX/`。

**文件名按用户现有习惯带项目前缀**：`<项目名>-<会议主题>纪要-<YYYYMMDD>.md`
（如 `四川省数字政府项目-一张图与地图数据采购讨论会纪要-20261109.md`）。
不要用日期当标题，也不要直接叫「XX会议纪要」而不带项目名。

**🚨 项目归属必须取证，不许凭印象套前缀。** 手上同一批项目（四川数字政府／陕西智慧民政）
的旧笔记一多，看到「数据平台大屏」「工作汇报」「专班」这类通用词就会顺手套上熟悉的那个。
定名前先从**转写正文**抓归属证据——机构名（省政数局、民政厅）、系统名（一体化数据资源
管理系统）、专题名（数据编目／汇聚／治理／赋能／安全）、地名、领导称谓，再用 `ls 00-INBOX`
对着同项目已有文件名核一遍。

套错的代价是连锁重做：文件名、frontmatter 的 `project`、`tags`、`related` 正向链接全要改，
还得把误加到**别的项目**笔记上的反链一条条撤掉。所以**宁可停下来问一句「这份属于哪个项目」，
也不要猜**——猜对了没人夸，猜错了要重来两遍。

**必须补 `related` 双向链接**：先去 `00-INBOX` 和 `concepts/` 搜同项目、同主题的旧纪要，
挑 2-3 篇相关的写进 `related`，并在对应旧文件里加一条反链。
同一主题的一系列会议（如空间地理库 → 一张图采购）串起来才看得出脉络。

### 6. 交付

微信推送一份 Markdown 摘要（不要全文），附入库路径。
用户要文件时**同时给一份 docx**（黑体标题 + 仿宋正文 + 楷体排录音原话），
比只给 `.md` 在手机上好读。写完用 python-docx 反向读一遍正文，确认关键词没丢。

**现成管线，不要手搓 docx 排版。** `scripts/md2spec_minutes.py` 把入库的 `.md` 转成
`cn_docx.py` 的 JSON spec（`##`→黑体 h1、`###`→h2、`>` 引述→楷体_GB2312、`- ` 列表→带 · 的段落、
表格→table 块、frontmatter 自动跳过），再喂给 `productivity/docx/scripts/cn_docx.py`：

```bash
python3 scripts/md2spec_minutes.py "<纪要.md>" "<spec.json>"
python3 skills/productivity/docx/scripts/cn_docx.py "<spec.json>" "<交付目录>/xxx.docx"
```

- `spec.json` **不要留在交付目录**（交付目录只放成品），用完挪进 `.tmp_tests/`。
- 反向校验跑三项：关键数字逐项 `in` 正文、手记要点逐项 `in`、`w:eastAsia` 字体是否写成
  （应出现黑体 / 仿宋_GB2312 / 楷体_GB2312 三种；缺了说明中文字体没生效，Word 里会回退）。

## 融合用户自带的手记

用户常自己记一份要点式纪要（docx 或纯文字），要求与 ASR 版融合。
**分层取信，不是一律以手记为准：**
**决议与措辞以手记为准**（谁负责哪块、哪件事先压着、领导具体嫌哪句——转写里抠不出来）；
**可核验的数量与指标以录音为准**——录音有原话数字时（「二十九个一件事」「百分之七十一点三」），
手记的速记数字经常写错或漏位。用户对这个分层的原话就是「以录音为准」。
两份说法冲突时不擅自取舍，两边都标出来（见下「待确认」与「口径说明」）。

- 手记条目逐条落地到「会议决议」，一条不能少；核对时把手记每条拆成一个关键词跑 `in` 检查，
  输出覆盖面 `n/N` 给用户看。
- 手记里的措辞原样保留：谁负责哪块、哪件事先压着、领导具体嫌哪句——这些转写里抠不出来。
- 转写补三类手记一般没有的：时间戳分段、具体数值与批次日期、「待跟进/时间安排」独立成段。
- **两份不一致的条目单列「待确认」**，写清各自的证据原话，让用户去定。
  典型：手记列了某模块要做，转写里却有人说「那我们就少画一个吧」——
  这种必须显式标出，不能悄悄按一边写。
- 两份条目都按主题重新分节（手记编号顺序保留脉络，但按业务分节），
  避免同一主题的内容散在两条里。

手记读取用 `python-docx` 直读，**同时看 `d.tables`**——有些手记正文整段在表格里，
只取 `d.paragraphs` 会读到半截。用户也可能直接把要点**当纯文本粘进对话**，
这时不必找 docx，按行解析即可。

### 🚨 只有手记、没有转写时：先做内部一致性核对

手记是现场速记，**同一份内部就会自相矛盾或写断**。用户催「纪要怎么样了」之前，
先清点并列出三类问题，**一律不许自行取舍或补全**：

1. **同一对象出现两个数量**——成效段写一个数、情况段写另一个数。两版并列进「待确认」，
   并替他把选项说出来（「是两类不同口径，还是其中一个记错了」），让他一句话就能定。
2. **条目写到一半断掉**——最后一条只剩一个动词。标 `【手记此处未记完】`，
   等录音补；录音里也没有就保留标记，**不要顺着上下文猜他想说什么**。
3. **枚举只说不全**——「形成 X 类等三大类」这类。原文照写，另列待确认「另外几类是什么」。

同时**分节报条目数**（总目标 n / 成效 n / 问题 n / 建议 n，合计 N 条），
让用户一眼看出有没有漏。骨架先在对话里过一遍、确认后再落文件，
不要一边缺信息一边写进 00-INBOX。

### 用户回改稿（第三轮，必然发生）

用户会拿你交的融合稿自己再改一遍发回来，说「这是我修改后的，请参考」。
**他删掉的一律不往回加**——那些删除多半是判断（某个待确认项他口头已经问清了、
某个细节不值得进纪要），不是笔误。

但两件事必须做：

1. **把他删了什么逐条报出来让他确认**。报告格式是「你另外删的 N 处，我照删，
   但列出来确认是不是有意的」，重点点出**要落实给别人、容易被漏掉的具体要求**
   （日程、更新年份、谁去做什么），纯版面动作可以轻轻带过。
2. **修编号断档**。删条目后流水号会留空（1–8 直接跳到 10）。重排成连续编号，
   并在回复里明说「内容和条数没动，只修编号」——别让他以为你改了他的内容。

回改稿常顺带了结前一轮的「待确认」项，逐项记下来（哪项定了、怎么定的），
确认完的处理分两种，别一律删：

- **纯争议项**（谁说了、要不要做）——处理完整节删掉，别留空壳。
- **口径类项**（同一对象出现多个数字、多个统计范围）——**不要删，改写成「口径说明」节保留**。
  它的结论本身就是纪要内容：哪个数为准、哪几个数各自指什么，后人读纪要要靠它。
  例：「供需匹配率取录音 71.3%」；「29 个已上线运行 / 27 个已确认发布 / 年底目标 25 个，
  是三个不同口径，同时成立」。同一事项出现多个数量时，**先判是不是不同统计范围，
  能自洽就分别写清口径，不要擅自合并或取一个**；判不了才进「待确认」。

用户删掉标题里的项目前缀时，**文件名仍带前缀**（跟库里其他同项目笔记排在一起），
H1 与文件名对齐，并在回复里一句话说明。

## 两种正文形态

用户的纪要库里两种都有，按会议类型选：

**A. 豆包式（默认，适合沟通交流/对接会）**

```markdown
## 总结
（一段话交代谁和谁、谈什么、定了什么方向）

## 智能章节
00:00
> 本章节是……（一段时间的内容概述）

08:22
> 本章节围绕……

## 关键决策
1. <决策内容>：<待明确事项>：<讨论过程谁说了什么>：<判断依据>：<后续推进>

## 金句时刻
「原话直引」
—— 为什么重要
```

**B. 政务式（适合工作部署会/培训/汇报会）**

```markdown
一、<大节标题>
1. <条目>
2. <条目>

二、<大节标题>
1. <条目>
注意事项：a…… b…… c……
```

判断：会上有明确分工/部署/培训讲解 → 用 B；多方交流、探讨方案、谈合作 → 用 A。

## 常见坑

- **`auto` 模式实测会误判**：一场公安侧与中心侧谈采购的对接讨论会，曾被判成「部署会」
  而用了政务式。判定规则已写死：对接会/交流会/讨论会/座谈会/需求对接一律豆包式，
  只有任务分解、责任分工、时限、培训才算政务式，**判断不了默认豆包式**。
  但用户指定结构时以用户为准，不要自作主张。
- **生成后必须自己逐条核对格式**，不能直接交给用户：H1 标题在不在、tags 是不是正好 10 个、
  summary 是不是 5 条且都带 ` ×`、金句有没有「——」点题行。模型经常漏其中一两项。
- **`transcript.json` 是 dict 不是 list**：结构为 `{model, audio, duration_s, text, segments, usage}`，
  段落必须取 `d['segments']`。直接 `d[:3]` 会报 `KeyError: slice(None, 3, None)`。
- **转写同名重复**：豆包导出的纪要在入库转换时会每段重复 2-3 遍（嵌套列表炸开）。生成的纪要自己写干净，别复制这种脏数据。
- **`关键决策` 字段名丢失**：豆包原稿有「决策内容/依据/讨论」等字段名，转换后变成空的 `​​：`。自己生成时字段名要写全。
- **会议日期 ≠ 笔记文件 date**：用户旧笔记的 frontmatter date 有过写成 `2026/06/22` 的错值。用会议实际日期。
- **不要把 `原始文件` 那行写死**：`> **原始文件**：xxx.md` 是笔记录入时加的，不是纪要内容。
