# 方案智能体 (Plan Writer)

专门用于撰写政务信息化方案、报告、建议书。采用**四轮制流程**（架构设计 → 用户确认 → 全文撰写 → humanizer去AI味），主模型为 DeepSeek 官方 `deepseek-flash`，备用百炼 `deepseek-v4.1-flash-1017`（主通道失败自动切换）。humanizer 融合在最后一步，确保输出读起来像人写的，没有AI味。

## 触发条件

用户说以下内容时加载此技能：
- "写方案" / "写个方案"
- "帮我写..."（指代方案/报告/建议书）
- "起草一份..."
- "工作总结" / "半年总结" / "年度总结"（个人或团队工作汇报类）
- "情况汇报" / "汇报材料" / "急需解决问题"（领导走访/问题汇报类）

## 模型配置

- **主模型**: `deepseek-flash`（**DeepSeek 官方**，即 DeepSeek-V4.1-Flash 最新版）
- **备用**: `deepseek-v4.1-flash-1017`（**阿里百炼 dashscope**）——主通道重试 3 次全失败后**自动切换**，无需手动干预
- **API**: 主 `https://api.deepseek.com/v1/chat/completions` / 备 `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`
- **Key**: 主 `DEEPSEEK_API_KEY` / 备 `BAILIAN_API_KEY`（均 `.env` 读取）
- **覆盖方式**：
  - `PLAN_PROVIDER=primary|fallback` 只跑单条通道（调试用）
  - `PLAN_MODEL` + 可选 `PLAN_API_URL`/`PLAN_KEY_ENV` 强制指定任意模型（会关掉自动切换）
  - `PLAN_THINKING=0` 关思考（**仅百炼生效**，官方接口不认 `enable_thinking`）
- **换模型依据**：官方 `deepseek-flash` 与百炼 `-1017` 质量无差别（各 3 次复核），选官方作主是因沿用原有 key 通道、无需跨平台；百炼作备用是跨厂商，官方全线故障时不会一起倒。

- **⚠️ 单次采样不可信**（2026-11-04 复核，各 3 次 × 380 字短任务）

| 模型 | 汉字中位（全距） | 思考占比中位 | 耗时中位 | 输出 token 中位 |
|---|---|---|---|---|
| 官方 `deepseek-flash` | 377（368~383） | 90% | 17.5s | **3081** |
| 百炼 `deepseek-v4.1-flash-1017` | 404（367~411） | 88% | 15.8s | 2517 |
| 百炼 `deepseek-v4.1-flash`（不带日期） | 383（367~416） | 85% | 14.4s | **1849** |

**教训：** 单次跑出的字数差异（曾出现 2301 vs 1675）落在噪声范围内，**全距重叠时不能判定"某模型思考更冗长"**。三家思考占比都在 79~91%，质量测不出差别，唯一稳定差异是输出 token 效率（差 67%）。仍用 `-1017` 而非不带日期版的理由：快照行为可预测，最新版虽省 27% token 但会随上游迭代变行为；2000 字方案里这点差价不到一分钱，稳定优先。**做模型对比至少跑 3 次取中位数。**
- **实测基线**（2026-11-04，2000 字政务方案章节，四模型同 prompt 各 1 次——字数差异见上方「单次采样不可信」，只看耗时/成本）

| 模型 | 汉字 | 耗时 | 成本 | 备注 |
|---|---|---|---|---|
| `deepseek-v4-pro` | 1860 | 136.9s | ¥0.0823 | 结构最完整但最慢最贵 |
| `deepseek-v4.1-flash-1017` | 2301 | **25.5s** | **¥0.0278** | 质量持平，快 5 倍、省 2/3 ← **现为备用通道** |
| `qwen3.8-flash` | 2358 | 164.5s | ¥0.0284 | 分段最均匀（10 节），但思考拖慢 |
| `qwen3.8-max` | 2135 | 266.3s | ¥0.3765 | 慢且贵 13 倍，无对应质量优势 |

四个模型均未编造数字、无"综上所述"类套话、均含分阶段落地收口。耗时与成本的差距是数量级的、跨样本稳定；字数差异不可依赖。

🚨 **官方的 `deepseek-v4-flash` 与它是什么关系**——官方 `/v1/models` 只有 `deepseek-flash` 和 `deepseek-v4-pro` 两个名字，**没有** `deepseek-v4-flash`（旧名兼容别名，路由到 `deepseek-flash`），也**没有** `deepseek-v4.1-flash-1017`（那是百炼的带日期快照名）。两者同为 V4.1 Flash、不同部署。**质量测不出差别**，稳定差异只在输出 token 效率。要多平台横向对比，load `llm-model-selection` skill，参考文档「qwen-vs-deepseek-flash-ab」有完整四模型长文实测表。

### ⚠️ 硅基流动已不可用（2026-10-10 实测）

硅基流动 V4-Pro / V4-Flash 均返回 **HTTP 402 账户余额不足**。旧配置（`deepseek-ai/DeepSeek-V4-Pro` + SILICONFLOW_API_KEY）已作废，不要再切回去。

### ⚠️ 推理型模型的静默陷阱（旧配置踩过）

DeepSeek 官方三个模型名，**是否产出 reasoning 完全不同**（实测：同一句 prompt，`deepseek-chat` 的 completion 只有 1 token，`deepseek-v4-pro` 有 29 token，差值全是 reasoning）：

| 模型名 | 接口返回的 model | 推理 | 适合 |
|---|---|---|---|
| `deepseek-chat` | `deepseek-flash` | **关闭** | 摘要、标签、格式化等机械任务 |
| `deepseek-flash` | `deepseek-flash` | 开启 | — |
| `deepseek-v4-pro` | `deepseek-v4-pro` | 开启 | 慢且贵，不推荐 |

**reasoning 与正文共用 completion 预算**。后果：max_tokens 给少了，reasoning 吃光预算，`content` 返回空字符串——**接口不报错**，脚本会把空文当成成功结果写进 docx（静默毁数据）。实测 `deepseek-flash` 写 200 字就烧掉 3733 completion token，长文场景尤其危险。

判据：看 `usage.completion_tokens_details.reasoning_tokens`，不为 0 就说明正文预算被思考侵占；再对比 `len(content)`，正文为 0 而 reasoning 很大 = 已经中招。

`call_llm` 已内置两道闸门（缺任何一道都会静默出空文件）：

1. **正文为空** → `RuntimeError`，并把 max_tokens 翻倍重试（上限 32000）
2. **finish_reason == 'length'**（被截断）→ 同样翻倍重试，绝不接受半截正文

三轮用尽仍失败则抛错，不会返回空串。call 点预算：第1轮架构 8000，第3轮全文 24000。

- **备用模型**: qwen3.8-flash（百炼 dashscope，输入 0.8/输出 2.7 元每百万 token，无峰谷价，支持视频输入）。关掉思考后一份 2000 字政务文段约 5s / ¥0.0008。**但实测它在复杂指令结构上会出错**——把「三个时间阶段 × 每段三段式」理解成「运营起点/成效/指标是三个阶段」，整篇作废；只适合当兜底，不要拿来顶替主模型写方案

## 工作流程

### 第1轮：架构设计（call_llm 第1次）

分析需求 → 检索知识库 → 输出：目录结构 + 每节核心论点 + 对比选型表格

**关键步骤：**
1. 助理根据用户需求，以终端命令格式调用 DeepSeek 官方 API 生成架构设计
2. 保存架构设计到 OutPut Box
3. **等待用户确认架构设计**（必须明确等待用户反馈，不能自动进入下一轮）

### 第2步：用户确认（人工审核）

架构设计生成后，**必须停下等待用户确认**。用户会审核目录结构是否合理、框架是否覆盖需求。
- 如果用户提出修改意见 → 调整架构设计，重新保存，再次等待确认
- 如果用户确认没问题 → 进入第3轮全文撰写

### 第3轮：全文撰写（call_llm 第2次）

基于确认后的架构设计 + 知识库参考内容 → 一次生成完整方案

**第3轮 Prompt 必须嵌入 humanizer 原则（从源头减少AI味）：**
- 不用"Additionally、Moreover、Furthermore、It is worth noting"等AI高频词
- 不用"stand as、serve as、marks a、underscores its importance"等空洞拔高句式
- 多用"是/有/要"等简单系词，保持平实
- **政务术语照常使用**："协同/抓手/赋能/闭环/深耕/彰显/体现"是本行业词，不是AI腔，不要回避
- 不用"不仅仅...更是..."的否定平行结构
- 不用"从X到Y"的假范围句式
- 不用"在...背景下/随着...的深入"等套话开头
- 具体数据前置，不用"显著/大幅/非常/极其"等量化不了的模糊副词；"有效提升/深入开展/切实保障"是正常书面用法，照常写
- 每个论点直接陈述，不加"值得注意的是/需要指出的是"等引导
- 结尾不写"展望未来/前景广阔/必将"等套话

**超时处理：** 全文生成超过 300s 时，加 `PLAN_THINKING=0` 重跑（百炼关思考，实测同一请求 completion token 从 142 降到 6、快 2.8 倍），并向用户说明是降级生成。仍超时则换 `PLAN_MODEL=qwen3.8-flash` 兜底。注意 `deepseek-chat` 是**官方**接口的关思考别名，百炼上不存在，切回官方时才用它。

### 第4步：Humanizer 去AI味（重要）

全文生成后，**必须逐项检查以下AI痕迹并修正**，再交付给用户：

#### 检查清单

| # | 检查项 | 处理方式 |
|---|--------|---------|
| 1 | **空洞拔高** — 找"stand as/serve as/marks/underscores its importance"等英文拔高句式 | 直接陈述，拔高句全删 |
| 2 | **AI高频词** — Additionally/Moreover/Furthermore/Notably/Vibrant/Robust | 替换或删除。⚠️ **注意"深耕/赋能/抓手/闭环/协同/彰显/体现/标志着"是政务术语，不在此列，一律保留** |
| 3 | **-ing 虚假深度** — "highlighting/underscoring/reflecting/ensuring/fostering showcasing"结尾的分词短句 | 去掉，直接说结果 |
| 4 | **否定平行结构** — "不仅仅...更是..."/"不是...而是..."/"It's not just...it's..." | 改成直接陈述 |
| 5 | **假范围** — "从X到Y"/"从A到B再到C" | 拆成逐条说明 |
| 6 | **套路开头** — "在...背景下"/"随着...的深入"/"众所周知" | **不是一删了之**：把状语里的信息并入主句或后置，删完必须还是完整句 |
| 7 | **模糊副词** — 显著/大幅/非常/极其（量化不了的） | 换具体数据或删掉。⚠️ **"有效/深入/切实"是正常书面副词，不是模糊副词，保留** |
| 8 | **引导句** — "值得注意的是/需要指出的是/不难看出" | 删掉，直接说内容 |
| 9 | **AI式结尾** — "展望未来/前景广阔/必将/Exciting times" | 补上主语后改写成事实性表述（如「项目将为X提供支撑」）。⚠️ 只删「展望未来」会留下「必将为X提供支撑」这种无主语残句 |
| 10 | **冗余填充** — "In order to"→"To"/"Due to the fact that"→"Because"/"At this point in time"→"Now" | 直接替换简洁说法 |
| 11 | **套话标题** — "背景与意义"/"现状与挑战"/"对策与建议" | 换成具体标题，如"为什么做"/"卡在哪"/"怎么干" |
| 12 | **过度修饰** — 每个论点前加"同时/此外/另外" | 删掉过渡词，段落自然起头 |
| 13 | **被动语态 / 缺主语** — "需要进一步完善"/"应当加强" | 加主语："我们需要完善"/"团队应当加强" |
| 14 | **规则3连** — 任何连续3个排比句、并列词组 | 合并或拆改，打破规整节奏 |

#### 操作方式

**两层处理，缺一不可：**

- **层一 `humanize_text()` — 结构层安全清理（零风险）**
  只做「删了句子仍完整」的清理：独立引导句（值得注意的是/需要指出的是/不难看出）、纯英文套话、多余空行。
  ⚠️ **绝不碰任何中文实词**——"有效/深入/切实"是正常书面副词，"协同/抓手/赋能/闭环/深耕/彰显/体现/标志着"是政务术语，一律保留。
  ⚠️ **2026-11-04 教训**：曾在正则里无条件删这些词，结果「有效提升A」→「提升A」变生硬、「展望未来，必将X」→「必将X」成无主语病句、「数据有效性」被拆成「数据性」。**正则删词做不了去AI味，只会做坏句子。**

- **层二 `humanize_llm()` — 模型句级改写（真正的去AI味）**
  AI 味是**句式病不是词汇病**：空心状语开头、无主语拔高收尾、机械排比、每段硬套"首先其次最后"、一句话拆两句说。这些只能重写句子解决。
  按段落切 2500 字一块，**4 并发放改写**（改写必须开思考，串行一块约 75s，一份 2 万字方案串行要 10 分钟，并发压到 2.5 分钟），**每块改写后过 `_humanize_guard()` 硬校验**：
  - 字数不得低于原文 90%
  - 数字/年份/百分比/标准号一个不能丢
  - 政务术语一个不能丢
  - 不得出现「必将/将为/必须/应当」开头的无主语残句
  **任何一项不过 → 丢弃该块改写、保留原文**。宁可留着 AI 味，也不能出病句或丢信息。
  想跳过层二：`PLAN_NO_HUMANIZE_LLM=1`

  ⚠️ **别想着给改写关思考提速。** 实测 `deepseek-chat`（官方关思考别名）2.9s 完成、比开思考快 26 倍，但会丢掉政务术语「标志着」、也不改写「在…背景下」，直接被 `_humanize_guard` 拦下。**速度问题用并发解决，不用降质解决。**
- 两层跑完再人工扫一遍检查清单，改写完自问「这段哪里像AI写的？」做第二轮
- 不改数据和事实准确性——humanizer 只动语言风格

**注意**：政务方案有特定文体（正式、严谨、数据密集），humanizer 不改变正式度，只去掉AI味。保留"当/应/须"等公文语体，只砍掉空洞拔高和套话。

## 格式要求

### 对比分析/借鉴要点类文档

用户偏好简洁格式：用数字编号（1. 2. 3. 4.），每点一段话即可，不加章节标题和表格，不展开多级结构。先给精简版，用户确认后再决定是否细化。

### 方案/报告类文档

按标准方案结构输出，但避免过度展开。优先让用户确认架构后再详细撰写。

### 工作汇报类

见下方特殊流程。

### 工作汇报类（工作总结/半年/年度总结）— 特殊流程

区别于政务方案（架构设计 → 完整提纲 → 逐节撰写），个人/团队工作汇报类总结采用 **一版成型 + 用户微调** 模式：

1. **整理源数据**：提取用户提供的 Excel Todo 清单、月报/周报、项目文档中的关键信息，按项目维度归类
2. **一版成型**：直接撰写精简版全文，不先出提纲，用户看结果再调
3. **格式要求（用户偏好 — 硬性）**：
   - **见事见数**：每项成果必须有具体事项+量化数据（任务数、金额量级、完成率等），不能写空话
   - **一段式**：全文一个自然段，不设多级标题（正文段落不分节），所有项目串成连贯叙述
   - **页数/字数**：个人总结严格控制 **300 字以内**，团队汇报控制在 500-800 字
   - **聚焦核心**：去掉非核心/边缘事项（培训、内部会议、日常沟通等），只保留有可量化成果的重大事项
4. **写作风格 — 突出成果，避免流水账 + humanizer去AI味**：
   - ❌ **不要**使用"参与""协助""完成"等被动/弱动词开头罗列做了什么（如"参与北京仿真平台建设，完成二期方案，赴延吉调研..."）
   - ✅ **要用**体现主导性和成果感的动词：**主导、牵头、推动、独立完成、实现、支撑**等
   - ✅ **成果前置**：先说取得了什么成果（如"成果获首信认可，实现一期到二期平稳衔接"），再提做法
   - ✅ **填补空白类表述**：如"填补团队在东北数据要素市场的空白""奠定基础"等，体现不可替代的价值
   - ✅ **去AI味检查**：特别留意"在...背景下""随着...的深入""值得注意的是""展望未来"等套话，全部删掉。300字内不要任何空洞拔高
5. **用户微调**：用户反馈后删除无效条目、调整措辞、压缩字数

### 问题汇报类（领导走访/急需解决问题）— 特殊流程

用于撰写面向高层领导的 **项目问题汇报材料**，如走访数据集团/政数局时的汇报文件。

**标准结构：**
1. **项目背景**（平台名称、主管部门、建设范围、已完成成果）
2. **当前面临的主要问题**（分条，每条+具体数据）
3. **恳请协调事项**（对应问题提出具体诉求）

**关键注意事项：**
1. **必须搜索知识库验证项目信息** — 不要依赖对话上下文推断项目名称和背景。用户纠正项目名称后，应重新搜索知识库确认
2. **问题描述要见事见数** — 每项问题必须有量化依据（投入金额、数据量、人员配置等）
3. **恳请事项必须对应具体问题** — 逐条对应，不能多一条或少一条
4. **正式公文格式** — 标题用方正小标宋简体（18pt），正文仿宋（14pt），小节标题黑体（15pt），问题子标题楷体（14pt）。落款写团队名称和日期
5. **用户反馈后的迭代** — 用户提出新增问题或修正描述后，全文重新生成，确保问题与恳请事项同步更新
6. **输出**：命名 `项目名称-急需解决问题汇报-YYYYMM.docx`，保存到 OutPut Box

## 已知陷阱

1. **max_tokens 不足** — 写完整方案需要 ≥ 8000 tokens（主备模型最大输出都 ≥ 131K，资源足够，别自己把预算给少了），否则会截断
2. **长文档超时** — 方案超 8000 字时可能 300s+ 超时。先用 `PLAN_THINKING=0` 生成全文（关思考，快数倍），再视必要性开思考精修关键章节。`deepseek-chat` 只在切回**官方**接口时才有意义，百炼上没有这个名字
3. **超时控制** — 方案较长时 API 调用可能超过 120s，设置 timeout=300
4. **备用模型** — qwen3.8-flash（百炼 dashscope）。**兜底可以，写方案不行**：实测它在复杂指令结构上会出错——把「三个阶段 × 每段三段式」理解成「运营起点/成效/指标是三个阶段」，整篇作废。仅当主模型连续失败时才切。
5. **工作总结不宜包含非核心事项** — 培训、内部会议、日常沟通、课题申报等边缘工作会稀释成果感。用户会要求删除这些条目，只保留有量化的重大成果
6. **不可遗漏表格内容** — 用户提供的 DOCX 月报/周报模板中，实际填写的成果往往在 **表格** 中（含完成率、关键节点等），不是段落文字。读 DOCX 时务必遍历 `doc.tables[]`
7. **字数压缩** — 早期版本容易写得过长。工作总结初稿控制在 300 字以内，如果用户反馈"字数太多"，进一步压缩的方法：去掉次级项目、合并同类事项、去掉修饰词只留数据
8. **问题汇报类先搜知识库** — 用户说"写错了"时，永远是自己的问题而非用户的。先搜索知识库（`concepts/` 和 `01-WeiXin/`）确认项目全称和背景，不要依赖聊天上下文推断
9. **项目混淆 — 动笔前核实项目名称**：当用户要求撰写关于某个特定项目的汇报/方案时，不要仅根据近期对话上下文推测是哪个项目。如果存在多个项目的上下文混叠，必须动笔前确认。个人工作类文档的核心数据源往往是用户此前提供的 Excel 任务清单/工作日志，而不是 Obsidian 知识库
10. **硬事实必须写进 prompt，否则它会编一个“听起来很像”的错答案** 🔴：拿同一个模型问“标准地址七级要素”，不给背景时它答“省、市、县、乡、村、街路巷、门牌号”——通顺、像样、全错（正确的是行政区划、街路巷、门牌、楼栋、单元、楼层、户室）。政务域的标准号、要素层级、阶段名称、指标口径这类东西，模型内部的“常识”不可信。**每轮 call 前把该节的硬事实（编码标准、层级、时间节点、可引用数据）逐条写进 prompt，并明确“不得引入未给出的信息”。** 知识库检索那一步的作用就是供事实，不是供文风。

## Humanizer 集成说明

本 skill 融合 humanizer 去AI味，三层：
1. **源头控制** — 第3轮 Prompt 嵌入 anti-AI 写作要求，模型写出来就少AI味
2. **层一 `humanize_text()`** — 正则做结构层安全清理（独立引导句/英文套话/空行），不碰中文实词，零风险、不调模型
3. **层二 `humanize_llm()`** — 调模型做句级改写，每块过 `_humanize_guard()` 校验（字数≥90%、数字标准号不丢、政务术语不丢、无无主语残句），不过就回退原文

**核心原则：去AI味是改句式，不是删词。** 正则只能删，删完句子就残；句式病（空心状语、无主语拔高、机械排比）只能重写句子解决。作为助理执行时，两层跑完仍要用第4步检查清单人工过一遍。
