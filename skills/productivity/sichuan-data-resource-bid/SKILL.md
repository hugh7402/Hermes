## 4. 述标演示脚本的硬要求（用户多轮纠正后定型）

1. **顺序严格按 215 三步 → 216 三步**，每步标「屏幕/路由」「操作提示」「口播」三块。
2. **口播是「应答」不是复述**：说清「要求什么—我们怎么做到—满足在哪」，不许把采购需求原文再念一遍。
3. **口播禁出现技术标识**：表英文名的值、GB/GB-T 标准编号、`YYYY-MM-DD` 之类格式串、系统路由。这些只留在「屏幕」「操作提示」栏供演示人自己看。写脚本要做自检断言。
4. **需求业务术语必须说**：一数一标准、一数一源、主关联字段、验证字段、保留原值、转换为权威数据、前置仓到归集仓、归集仓到清洗仓。数字念中文（一千条、九百六十八条）。
5. **字数**：演示与操作同一人 → 口播只占全场 50~60%。**口播 ≈1350–1450 字（约 5.5 分钟）＋ 操作预留 4 分钟 ≈ 9.5–10 分钟**；上限 1500 字。
6. **去 AI 味**（述标场景）：不用破折号堆叠、不用三段排比、不用「都落地了 / 就在这里闭环」式口号收尾；称呼用「各位专家」；第一人称讲话（「我演示的是…」）。
7. **用户会自己改一版**，此后一律**在其改版的 docx 上做增量修改**（保留其标题、删改、格式），别重写整个文档。当前用户改版标题为「**一树一眼 · 演示脚本**」。
8. **增量改写的实操（docx）**——不要重写整篇，按段落替换：
   ```bash
   # 读结构与文本（先看用户改了什么、断了哪些小节）
   python3 /opt/data/skills/productivity/docx/scripts/docx_read.py "<用户版>.docx" --structure
   python3 /opt/data/skills/productivity/docx/scripts/docx_read.py "<用户版>.docx" --text
   # 改：python-docx 按“段落前缀”定位，用 p.runs[0] 承接字体/字号，删掉其余 run，再 first.text = 新稿
   # 校验（改完必跑）
   python3 /opt/data/skills/productivity/docx/scripts/docx_validate.py "<产物>.docx"   # 期望 {"ok": true}
   ```
   坑：① **用户删过小节后序号会断层**（出现「一、…三、…」），顺手重排；② 口播稿是整段长文本、Word 常拆成多个 run，
   **按段落前缀定位比按 run 定位稳**；③ 改完抽样比对新旧段落的字体/字号（宋体 11pt）确认没改坏格式；
   ④ 交付时把用户原版另存一份（如 `…_用户改版_原始.docx`）留对照，旧版归入子目录。
9. **口播字数按 250 字/分钟算并当场核算**：写完脚本用脚本统计汉字数（`len(re.findall(r'[\u4e00-\u9fff]', t))`），
   逐段列出字数与秒数、给合计，超上限就砍最长的段（通常是收尾的六步复述）。

## 5. 投标方案审核（三层法，先保命再看分）

1. **废标级**：★注条款（唯一产品 / 进口产品 / 强制节能产品认证）；21 条 ▲ 逐条响应且不得负偏离；第五章符合性审查表逐项；报价 ≤ 119,000,000 元；形式要件（签章、装订、份数、密封、保证金，在投标人须知）。
2. **评分级**：技术方案对评分表逐项覆盖；**215/216 现场述标演示要能真跑通**；商务分材料（业绩、资质、人员）；价格分策略。
3. **质量级**：逐条应答/偏离表与正文口径一致；技术方案、报价表、工期承诺、团队名单四处不打架；性能容量指标不自相矛盾；不承诺超出能力的指标；引用标准现行有效。

常见翻车方式：「应答满足」但正文对应章节没有内容；把 ▲ 当扣分项而实际是实质性；用旧版招标文件的限价/参数。

## 6. 初设正文撰写（建设内容／应用场景／评价标准）

用户在初设（`【AI版】某省数字政府项目…初步设计方案1005.docx`，微信落到 `/opt/data/cache/documents/`）上逐模块补写，
每个模块只要三样：**1. 建设内容　2. 应用场景　3. 评价标准**，每样**一段话**，不分条、不展开。

### 定位模块：标题是自动编号，搜 "5.2" 是搜不到的

普通段落里根本没有章节号（Word 自动编号不进 `w:t`）。用户说的「5.2 开放门户」在文档里其实是 **9.5.2 开放门户**。
正确做法：遍历段落，按 `style.name` 数 Heading 1/2/3 的层级，还原出 `9.5.2` 这样的路径再定位；
再用「下一个 Heading ≤3」当区间终点，把区间正文导出到 `/tmp` 再分段读（体积大：实测 38,091 段 / 166 表）。

**别用「标题文本 → 段落索引」的字典定位**：H1/H2/H3 里存在同名标题（如两处「项目建设目标」），dict 会互相覆盖、目标键反而抛 KeyError；
一律用「起点索引 + 下一个同级标题索引」的区间，索引从上面那次遍历的输出里直接抄。

**几千段的章节不要整节读**：抓三样就够写三段了——① 该节首部「系统概述 / 系统设计」的前 3～4 段（带建设思路）；
② 文中「共包含 N 个一级功能模块：…，合计提供 M 项功能」那一句（模块名与功能点数都在里面）；③ Heading 4/5 的模块清单做校验。
按 200 段一批切分取，避免一次输出撑爆上下文。

```python
from docx import Document
d = Document(path); h1 = h2 = h3 = 0
for i, p in enumerate(d.paragraphs):
    st, t = p.style.name, p.text.strip()
    if not t: continue
    if st == 'Heading 1': h1 += 1; h2 = h3 = 0; print(f'[{i}] {h1}. {t}')
    elif st == 'Heading 2': h2 += 1; h3 = 0; print(f'[{i}] {h1}.{h2} {t}')
    elif st == 'Heading 3': h3 += 1; print(f'[{i}] {h1}.{h2}.{h3} {t}')
# 区间：[start, 下一个 Heading 1~3 的段落 index)
```

### 三段各从哪里取

| 段 | 取材位置 |
|---|---|
| 建设内容 | 该节「系统设计 / 建设内容」子标题下的功能点（终端划分、功能模块清单、数据申请与互动交流、无障碍、移动端、智能问数等） |
| 应用场景 | 面向对象与使用流程：谁登录（数字政府统一身份认证）、怎么找数据（按场景/领域/部门/字段）、怎么用（预览/下载/API/数据需求申请）、开发者怎么用、特殊人群怎么访问 |
| 评价标准 | **通用章节「性能需求分析」（4.6.2）里的量化指标** — 用户层含门户的活跃并发用户数≥200、查询类接口吞吐量≥150TPS（1 次接口调用计 1 个事务）、简单查询 P95≤2s、复杂统计查询 P95≤8s、首屏可交互 P95≤2s；安全取分区分域（互联网区 SSLVPN+SSL 证书、国密算法）；再加无障碍/适老化 |

**指标只用原文有的** —— 评价标准一写不出数字就等于没标准，但不许自己造指标；原文只给了并发/吞吐/响应时间这类，就写到这个粒度为止。

**评价标准必须写两样东西，缺一样就被打回**：① **功能验收**——建成后应包含哪些模块、形成什么访问形态；② **性能指标**——原文量化值。只写性能会被当场纠正，用户给的正确写法是「门户建成后应包括开放目录、数据图谱、开放指数、APP 应用、数据申请、互动交流等功能，为个人、机构提供数据开放服务，并形成电脑端和移动端双端访问；同时满足并发用户不低于 200 ……」。功能在前、指标在后，同一段里融掉。

### 篇幅与交付

- **篇幅：每段约 100 字**（实测 108 / 97 / 105 字过关）。用户对 300 多字的版本回过「文字太多了，缩减到 100 字左右」——
  建设内容只留「依托什么 + 干什么 + 关键模块」三件事，应用场景一句话（面向谁、支撑什么），评价标准功能+指标各一句。
- **默认只交文字，不交 docx**：用户明说「不用发 word 版，直接给我文字即可」，他会直接粘回初设。
  只有他明确要文件时才写 docx；真要文件就 `docx_create.py` 的 JSON spec（标题黑体、正文仿宋 12pt）存 `OutPut Box/某省初设_<章节>_三段内容_<YYYYMMDD>.docx`。
- **要求「整合成 1–2 段」时去掉序号**：把「1. 重点产品／2. 重点商机／3. 规模以上项目」这类并列条揉成两段连贯表述，
  每段首句提纲挈领（「重点产品方面，…」「重点商机与规模以上收入项目方面，…」），不再出现 1./2./3.。
- **原文地名被脱敏成「某」**（如「某与重庆数据平台的级联互通」）——不要替用户猜具体地名，写「跨区域」并在交稿时点明让他替换。

### 表格形态（系统 / 建设内容 / 应用场景 / 评价标准）

用户会给一个 xlsx 模板（首列「系统」，后三列对应三段），要求**按同一模板逐系统填**。实测口径：

- 范围按初设第 9 章走：用户层 5 个（共享门户、开放门户、公共数据资源登记门户、公共数据资源授权运营管理门户、数据资源系统工作台）
  ＋ 应用层 21 个（电子证照、数据共享、数据开放、公共数据资源登记、数据资源调查、决策支撑、应用服务、数据编目、一数一源、数据高铁、
  数据供需对接、数据归集、数据融合分析、模型管理、数据质量评估、数据服务管理、全链数据血缘、监控管理、数据全景地图、公共数据授权运营管理、系统管理）。
- **建设内容 80～190 字**，带上原文的关键量化（如「15 个一级模块、合计 3911 项功能」）；**应用场景一句话**；
  **评价标准固定 5 条清单**（这就是用户的表内标准，别再写成长段）：
  `1.完成所有功能模块开发；2.完成与相关子系统对接；3.关键流程可闭环／三级用户体系贯通；4.具备上线条件；5.符合安全与性能要求，通过相关测评。`
- 用 openpyxl 追加行、`Alignment(wrap_text=True, vertical='top')`、列宽 A22/B62/C40/D34，另存新文件名交付（别覆盖用户原表）。
- 交付时列一句「一处需你确认」——脱敏地名、或归属存疑的模块，集中问，不要散在各行里。
- 交稿时点出两个判断点：① 用户说的节号与文档实际节号可能不一致（如 5.2 ↔ 9.5.2），说明我按哪个对齐；② 该节下如果还挂着别的模块（如「数据要素×大赛」），**不属于本模块本体**，问一句要不要并入，不要默默塞进去。

## 7. 工程教训
