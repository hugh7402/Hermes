# 验收成效指标：运营 ↔ 平台建设 两表交叉核对

客户的硬要求：**平台建设里凡是前面有运营成效指标的，都要在「评价与验收标准」末尾挂一句引用运营指标**，
运营侧没有对应条目的（如数据可视化系统）不挂。任务是「检查有没有没对应上的，并按同样措辞补上」。

## 表结构（用户给的文件，两个 sheet）

`验收成效指标-运营`（约 60 行）：序号 / 运营主线 / 运营任务 / 验收指标（建成要件） / 2026年底 / 2027-02 初验 / 2027-05 终验 / 需协同条件 / 依据条款／标准 / 验证方法

`验收成效指标-平台建设`（约 64 条）：序号 / 分类 / 板块 / 系统 / 子系统 / 建设内容 / 应用场景 / **评价与验收标准（H 列）**

B/C/D/E 列大量纵向合并（同一系统下的多个子系统只写一次系统名），读的时候要顺延上一行的值补全。

## 最大的坑：H 列也是合并的

`ws.cell(r, 8)` 对合并区里非左上角的单元格返回 `MergedCell`/`None`。直接扫一遍会得出
**「20 多行没有评价与验收标准」的错误结论**，进而想逐行补——而实际上一个合并区只有一处可补。

正确姿势：先把合并区映射成 `anchor[行] = 左上角行`，按存储行去重再统计。实测安全系统整段
（序号 4–28，25 个网络安全/数据安全子系统）共用 `H6:H30` 一个单元格；序号 63/64 共用 `H65:H66`。
所以「42 条没挂」去重后只有 **17 个位置**要处理。

```python
anchor = {}
for m in ws.merged_cells.ranges:
    if m.min_col <= 8 <= m.max_col:
        for r in range(m.min_row, m.max_row + 1):
            anchor[r] = m.min_row
ev = ws.cell(anchor.get(r, r), 8).value      # 取值一律走这张表
```

## 措辞：照抄表里已有的句子，不要自己造句

表内已成型的句式只有两种，序号接该单元格现有条目数往下排（`count_items = len(re.findall(r'(?:^|\n|。|\s)(\d+)、', text))`）：

```
{N}、支撑保障{运营主线}的运营成效指标达成。详细参见数据运营成效指标。
```

`{运营主线}` 必须**逐字取自运营 sheet 的「运营主线」列**（含全角括号，如「公共数据（数据要素市场化）」），
否则评审一对表就看出是两套口径。现有写法少见地挂了两三条主线的（如「数据共享、数据回流」），可以照此并列。

## 两个必须回报的上游问题

1. **运营 sheet 没有「数据登记」这条主线**，而平台建设侧有 3 处涉及登记（国省协同服务 / 登记门户 / 登记系统）。
   三处无处可挂。要么运营侧补一条（登记量、登记覆盖率、登记凭证核验率），要么平台建设侧书面说明「运营侧暂无对应指标」。
2. **已写的引用可能挂空**：序号 45「商圈和景区分析应用服务」写了自己作引用主体的句子，
   但运营侧「重点应用场景」只有 6 条（地理空间、川渝、商贸流通、天府地址码、人房要素协同、决策支撑），没有商圈和景区——
   建议改成「重点应用场景」或把该场景补进运营表。**核查时要顺手把已挂的 22 条也验一遍能不能对上主线名**，
   别只查缺的。

## 反向核对：运营 → 平台建设（用户会反过来再问一次）

同一对表，用户会换方向再问：「筛一下运营指标是否都能对应到平台建设指标，没对应的列出来我来处理」。
方向不同、结论不同，**不能拿正向的清单直接反推**（正向查的是平台侧缺引用，反向查的是运营侧无建设载体）。

### 方法：先声明，再搜关键词

1. 把平台建设 64 项里已写的引用句抽出，`支撑保障(.+?)的运营成效指标达成` → 拆顿号 → 归一到 17 条主线原词，
   得到「哪些主线被声明过」。主线名与任务名要两级归一（如「电子证照库」「政务服务应用服务」是任务名，要归回其主线）。
2. 剩下来没被声明的，**不能直接判无对应**，要在「系统 + 子系统 + 建设内容」三个字段里搜关键词：
   密码 / 商密 / 密评 / 采购 / 川渝 / 回流 / 自然人 / 法人 / 信用 / 主题库 / 专题库 / 基础库 / 标准。
   搜到 0 处才是真无承载力。
3. 一线一线的看**“建”还是“用”**：`地理空间应用服务` 是消费空间地理库的应用，不等于「空间地理基础库建设」，
   不能算专属承载（否则「基础库」全被算成已覆盖）。同理 `数据融合分析` 一句话捐了「基础库、主题库、专题库」，属笼统。

### 三档判定

| 档 | 标准 | 实测条数 |
|---|---|---|
| A 有专项承载 | 平台侧有对应系统，且引用句已声明该主线 | 42 |
| B 仅笼统承载 | 只靠通用系统（数据融合分析/数据共享）一句引用盖住，无专项建设内容 | 13（基础库 4 + 主题库 5 + 专题库 2 + 数据回流 2） |
| C 完全无对应 | 64 项里搜不到任何相关系统或建设内容 | 7（数据采购 4 / 商密改造 1 / 川渝应用服务 1 / 标准规范 1） |

### 处理建议要分两类，不要一律“补建设内容”

- **该补平台建设行的**：**数据采购**（采购数据要有接入/治理/落库的落脚点）、**商密改造**（密评要求系统本身具备密码应用能力，不是服务能替代的）。
  这两项与花钱、验收直接挂钩，不写进平台建设范围容易被卡。
- **应归运营/服务范畴、在运营表注明即可**：**标准规范**（编制标准是咨询工作）、**川渝应用服务**（跨省协同数据服务）。
  在运营 sheet 的「验证方法」里加「本项由 XX 服务承担，不涉及平台建设内容」，比在平台建设里硬加一条没内容的项更稳。
- 反向顺手会抓到「平台侧多出的」项（运营侧没指标）：数据可视化系统（客户已说不用）、数据登记三类、隐私计算、
  数据要素×大赛、统一信息查询、全链血缘、监控管理、协同管理——这一页也要给，但不能与 C 档混为一谈。

### 交付

同样只出清单不改表：`OutPut Box/运营指标_平台建设对应情况核对.xlsx`，五个 sheet：
汇总（A/B/C 条数与含义）/ 对应情况总表（62 条按档标色）/ 完全无对应（带建议处理方向）/ 仅笼统承载 / 反向：平台建设多出的。
聊天里只报 C 档 7 条与 B 档 13 条的名称 + 一句“真正该补建设内容的是哪几个”。

## 交付形态：只出清单，不改用户的表

用户原话：「需要补充的你可以单独列出来，告诉我对应到那个部分补充即可」。

- **绝不覆盖或另存替换他的 xlsx**，只交一份清单：`OutPut Box/平台建设_需补运营成效引用清单.xlsx`，三个 sheet：
  「需补清单」（存储单元格 / 序号 / 系统 / 现有条目数 / 补的序号 / 挂的主线 / **可直接复制的原文** / 依据 / 建议强度）、
  「不补的」（+ 原因）、「Sheet1缺口提示」。
- 清单必须能让人**照着贴**：给出 H 列确切单元格（`H6`）、现有条目数、该接的序号、完整句子，不要只写「建议补」三个字。
- 正文里按「需补 / 不补 / 上游问题」三段讲，表格列 10 行以内，别把整张表贴进聊天。

## 版本

用户会连发多个带时间戳的同名文件（如 `…1030-1910.xlsx` → `…1030-1935(2).xlsx`），**一律以最新时间戳为准重跑**，
不要拿上一版的结论去改新一版——行数与合并区都可能变。
