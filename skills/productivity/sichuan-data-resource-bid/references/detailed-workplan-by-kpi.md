# 按示例颗粒度编制「详细工作计划表」并对齐三阶段指标

适用：用户给出一个多 sheet 的工作簿——一个「示例」sheet（已有颗粒度参考）、一个「指标成效」sheet（三阶段目标）、
若干个空白的目标 sheet——要求「按示例的颗粒度和内容编制计划填进去」。
实测对象：天府交易专题库工作、标准规范体系 工作。

## 一、动手前必须摸清三样

| 要摸的 | 怎么摸 | 摸不到会怎样 |
|---|---|---|
| 示例 sheet 的颗粒度 | 逐行导出：工作分类 / 工作项 / 工作细项 / 责任岗位 / 起止 / 时长 / 交付物 | 编出来的行太粗（一条顶示例十条），用户会说「颗粒度不够」 |
| 指标成效的三阶段目标值 | 逐字抄「2026年底 / 初验 / 终验」三列的成效目标值 + 建成要件列 | 排期没有锚点，会把 2027 的活排进 2026 |
| 目标 sheet 的表头与格式 | 列宽、表头字体/底色、日期 `number_format`、是否合并单元格 | 填出来跟示例长得不一样，得返工 |

**旧版 `.xls`（BIFF）用 xlrd，新版 `.xlsx` 用 openpyxl**。同一次任务里两种格式同时出现是常态（示例是指标工作簿 .xlsx、
标准清单是 .xls），不要拿 openpyxl 去开 .xls 然后报错。

## 二、颗粒度对齐：照抄示例的「形状」，只换内容

示例的典型形状（一个专题库 ≈ 60～80 行）：

```
方案编制(1) → 供需对接(11) → 对接模式及需求验证(10) → 数据汇聚(6)
→ 数据归集治理(11) → 数据开发(10) → 数据服务(9) → 数据质量提升(8)
```

- **工作细项控制在 1～3 天**（列头写的就是 ≤3 天）；确有长任务写成一个细项但时长可以到 7～9 天，不要硬拆成假动作。
- **责任岗位只取示例里已有的取值**（数据架构师 / 需求分析工程师 / 数据开发工程师 / 数据汇聚工程师 /
  数据归集工程师 / 数据治理工程师 / 数据质量工程师）。标准编制类可加「标准化管理工程师」「数据标准工程师」这类
  与清单业务对口的岗位，但不要凭空造「数据专员」。
- **每条细项必须给交付物**（需求清单 / 数据对账表 / 调试的任务 / 测试报告 …），示例每一行都有，缺了就显空。
- 同一条「工作分类」只写在组的首行，其余行留空后**纵向合并**（示例就是这么做的）。

## 三、阶段划分：严格照「指标成效」三列走，不许抢跑

三阶段节点是固定的：**2026 年底 → 2027 年 2 月（初验） → 2027 年 5 月（终验）**。

- **当阶段只交付当阶段的目标**。终验才要的「支撑围标串标识别、评标专家违规识别、交易异常识别 3 类监管场景」，
  在 2026 阶段的细项里**只能写「预留分析型数据组织方式，为后续…预留分析基础」**，不能写「支撑…」。
  同理初验才要的 2 类服务场景，2026 阶段写「预留支撑」。
- 直接把后期目标写成当期成果 = 虚报，评审一对指标表就露。
- 每个阶段的末尾加一个「阶段收口」分类：成效目标自评（逐条对着指标成效抄目标值）+ 交付文档归档，
  这是验收取证的抓手，不要省。

## 四、标准清单类任务：先分类，再按阶段切批

拿到 N 条标准清单（实测 71 条），**不要一股脑全排进第一个窗口**。做法：

1. **按指标成效的 7 类生命周期给每条标准归位**：数据编目 / 归集 / 治理 / 共享 / 开放 / 授权运营 / 安全管理。
2. 统计各类条数，与指标成效当期要求的范围对照。实测：71 条里属于 7 类的只有 **49 条**，
   其余 **22 条**是平台建设、基础库、质量、应用服务与运维、制度机制等支撑类。
   → 2026 年底只交 49 条；22 条 + 指标要求的 3 套指南排到 2027 年 2 月前。
3. **先查指标要求的类别在清单里是否真有条目**。实测「授权运营」类在 71 条里是 **0 条**，
   但指标明确要 7 类——这类缺口必须先摆给用户定（新增一条 / 扩写现有某条覆盖 / 备注缺口语），不要自己默默补。
4. **每条标准拆两个细项就够**：起草（3～5 天，细项带上清单里那句「功能/服务描述」）+ 内部评审（2 天）。
   外部意见征询、专家评审、推广试用按三阶段放到 2027 年，**在细项末尾写明「列入 2027 年计划」**，避免被当成漏做。
5. **并行流数按人月反算并明说**。71 × 1.2 人月 = 85.2 人月，压进 47 天需要几十人并行——
   这个假设必须写进「划分编制批次与分工」那条细项里（比如「第一阶段划分 12 个编制组：编目2、归集2、治理2、共享2、开放1、安全3」），
   并在交付说明里点明「若实际投入没有这么多组，分工表要一起改」。

## 五、openpyxl 照抄示例格式的配方

```python
# 先把示例 sheet 的格式读出来，再照抄
for col in ws.column_dimensions: print(col, ws.column_dimensions[col].width)
print(ws.cell(1,1).font.name, ws.cell(1,1).font.size, ws.cell(1,1).fill.fgColor.rgb)
print(ws.cell(2,6).number_format)      # 日期列通常是 'yyyy/mm/dd'
print(ws.merged_cells.ranges)          # 工作分类列的纵向合并区间
```

- **表头**：`微软雅黑 9 bold`，底色常见 `FF2F5597`（深蓝），`center/center + wrap_text`。
- **数据行**：`微软雅黑 9`，文本列左对齐、其余居中，全部 `wrap_text=True`，细边框，行高 30。
- **日期必须写 `datetime` 对象 + `number_format='yyyy/mm/dd'`**，写字符串会导致排序和筛选失效。
- **改写目标 sheet 前先确认它原本是否为空**（表头在、数据行为空）。
- **原样保留示例 sheet 与指标 sheet**，只填目标 sheet；另存新文件名交付，别覆盖用户原表。

## 六、多阶段排期最容易犯的错：偏移量基准不统一

各阶段的偏移量是相对**各自阶段起点**写的（初验第 0 天 = 初验阶段首日），但写入时往往统一用
**第一阶段起点**做基准 → 三个阶段的日期会全部叠在开头那个窗口里。

```python
# 错：三个阶段的 0 都落在 P1S
trade = P1 + P2 + P3
# 对：先把各阶段偏移换算成相对 P1S 的绝对偏移
p2off = (P2S - P1S).days
p3off = (P3S - P1S).days
trade = P1 + [[c,i,d,ro,o+p2off,du,dv] for c,i,d,ro,o,du,dv in P2] \
            + [[c,i,d,ro,o+p3off,du,dv] for c,i,d,ro,o,du,dv in P3]
```

**症状**：所有任务日期挤在开头十几天、阶段条数汇总对不上。**排查**：按阶段起点分桶统计条数，看合计是否等于总行数。

## 七、交付前必跑的校验（逐条都要过）

1. **越界**：起止日期是否都在计划窗口内。
2. **时长自洽**：`时长 == (结束 - 开始).days + 1`，逐行算。
3. **阶段分桶**：每个阶段桶的条数之和 == 总行数（漏一天就会被发现）。
4. **参考清单全覆盖**：把清单里的名称逐个与表内「工作项」比对，缺一条都不行；同时列出「表内出现但清单没有的」条目
   （这些通常是前置任务，属正常，但要解释清楚）。
5. **指标关键词覆盖**：把指标成效的目标值拆成关键词逐个 grep 表内细项，例：6 个环节名、接口可用率 99%、
   3 类监管场景名、基础库关联、电子证照调用等。
6. **序号连续**、`max_row` 与任务数一致。

**校验写完要能打印 ❌ 和样例行号**，不要只返回 True/False —— 出问题时直接看到是哪一行。

## 八、交付时必须向用户点明的判断点

集中列在文末，一条一句，不要散在各处：

- 阶段怎么切的、为什么这么切（对应指标成效哪一列）。
- 哪些是清单里没有、我扩写覆盖的（如授权运营由《公共数据开放工作指引》扩写）。
- 并行度是按多少人算的（人月 ÷ 工期反算），与实际投入不符时哪条要改。
- 哪几条可能是重复计价（如 3 套指南与清单里已有标准内容交叠），要用户定是引用还是独立编制。
- 清单里工作量若是一刀切（实测 71 条全写 1.2 人月 / 2.4 万元），提示这只是均摊占位值，
  并问要不要按标准实际分量分档排期（重档 5～7 天 / 中档 3～5 天 / 轻档 2～3 天）。

## 九、用户纠正过的排期口径

**「太激进了，年前不太可能完成所有标准」** —— 排期节奏必须服从指标成效的阶段目标，
不是为了「把窗口填满」就把全部工作压进第一阶段。窗口有余额时，宁可把余量留给收口与缓冲，
或按阶段后移，不要用来制造不可能完成的并行度。
