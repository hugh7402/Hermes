# 子系统「建设内容 / 应用场景 / 评价标准」填写与审查规范

用于四川一体化数据资源管理系统投标/初设阶段：给各系统负责人下达填写要求，或审查分工表（xlsx，列：序号、分类、系统/板块、功能模块、子模块、责任人、建设内容、应用场景、评价标准）。

## 一、系统清单（共 26 个，来自初设第 9 章）

用户层（9.5，5 个）：政务数据服务门户（共享门户）、开放门户、公共数据资源登记门户、公共数据资源授权运营管理门户、数据资源系统工作台。

应用层（9.6，21 个）：电子证照系统、数据共享、数据开放、公共数据资源登记、数据资源调查、决策支撑、应用服务、数据编目、一数一源、数据高铁、数据供需对接、数据归集、数据融合分析、模型管理、数据质量评估、数据服务管理、全链数据血缘、监控管理、数据全景地图、公共数据授权运营管理、系统管理。

关键规模数（写建设内容时的量化抓手）：数据资源系统工作台 8 个一级模块 / 1757 项功能；数据编目 15 个模块 / 3911 项功能；数据归集 16 个模块 / 1843 项功能；数据高铁 10 个模块 / 1506 项功能；数据供需对接 6 个模块 / 2461 项功能；数据共享 9 个模块 / 44 个二级模块；公共数据资源登记 71 个二级模块。

## 二、两个标准模板（用户标黄行，所有行必须对齐）

### 库仓类 → 以「自然人基础库」为模板
- 建设内容：「以 X 为基础，整合 A、B、C 等多部门……信息资源建设 X，实现四川省……全过程归集与治理，支撑……行业和领域应用。」（约 110 字）
- 应用场景：「为『高效办成一件事』、天府 X 等跨部门、跨层级政务应用场景提供……数据支撑；面向省级部门、市（州）属地化业务、政务服务事项等多跨场景，提供……数据核验、查询接口及库表同步的数据支撑。」（约 95 字）
- 评价标准：一段总述（部门数据归集与标准化治理、统一汇聚与全过程覆盖、完整性/准确性/时效性、数据规范与质量校验）+ 3 条量化：①相关数据归集率 100%；②主要数据校验率、覆盖率（存量+增量）100%；③数据更新率 99%、数据质量达标率 90%。（约 243 字）

### 系统类 → 以「数据开放」为模板
- 建设内容：分条列举（1、2、3、4 具体功能与能力），约 250 字。
- 应用场景：一句话写清面向谁、提供什么服务（模板仅 27 字：面向社会公众、企事业单位和机构用户，提供数据开放服务）。
- 评价标准：2 条——①周期性评价成效指标（如数据开放率、开放清单、中国开放数林指数排名）；②完成所有功能模块开发、对接、统一身份认证、测试、安全性能等相关测评，具备上线条件。（约 164 字）

## 三、审查规则（12 条，逐行跑）

库仓类判定：系统/板块含 前置仓、归集仓、治理仓、应用仓、数据采购 之一即算库仓；该格为空时沿用上方最近的非空板块。

1. 未填写：三栏全空 → 最高优先催（本次 7 行全在同一人名下）。
2. 库仓建设内容字数：<80 或 >220 字告警（模板 110）。
3. 库仓应用场景字数：<40 或 >200 字告警（模板 95）。
4. 系统应用场景字数：<15 或 >160 字告警（模板 27）。
5. 系统建设内容字数：<60 或 >500 告警（模板 249）。
6. 评价标准偏长：库仓 >300 字、系统 >350 字告警。
7. 库仓评价缺量化：缺「归集率/覆盖率/更新率/达标率/合格率」中 3 项以上即判缺。
8. 系统评价缺测评/上线：缺「测评」或「上线」关键词。
9. 系统评价无成效指标：无「周期/指数/排名/率/不少于/覆盖」类表述。
10. 库仓建设内容缺要素：缺「以X为基础」「整合」「归集/汇聚」「支撑」中 2 项以上。
11. 库仓应用场景缺要素：缺「高效办成一件事」「市（州）属地化业务」「核验/查询接口/库表同步」中 2 项以上。
12. 评价标准条目不足：库仓 <80 字、系统 <45 字。

输出：在原表加 J 列「备注」（黄表头 FFF2CC，列宽 60～78，自动换行）；无问题的行留空，方便筛选。

## 四、交付偏好（用户明确要求，别违反）

### 备注写法必须跟用户手写的那几行

用户会先自己改几行备注、然后要求「按我加的备注形式和方式，对其他条进行备注」。他那一版的形式就是标准：

- 单条问题**不加编号**；多条用 `1.` `2.` `3.` **分行**（单元格内换行），不要用「；」把几条连成一句。
- 每条 = **问题 + 处置动作**，写成可执行的短句：「建设内容文字精简合并」「去掉性能要求」「评价标准缺（测评、上线条件）条目」。
- 不解释为什么、不复遍指标全清单（量化只写「缺量化指标（归集率、覆盖率、更新率、质量达标率）」）、不写「需按模板补写」这类结尾。
- 字数超标统一写「文字精简合并」，不标具体字数；**只有内容过短**才写「按模板句式补（以X为基础、整合多部门、支撑行业应用）」——短内容说「精简」是反的。
- 用户已填的行原样保留，只补空行；交付前把保留/新补的行数报一句。

### 单品压缩改写（用户会说「内容过多」「修改一下」）

初稿提交后的下一句往往是「文字过多」，这时**不要只给一版**，固定交付这个格式：

1. **两版并列**：版本一（要素全，约 130～150 字，括号里保留对应评分点的功能项）／版本二（极简，约 110～125 字，删运维类细项）。
2. **一句「改动逻辑」**：N 条编号并成「A—B—C」几个分句；共性能力只写一遍；删掉纯拔高句（「实现从宏观态势到微观主体的穿透式分析」这类）；重复名词第二次用简称。
3. **点明取舍**：列出被删的细项（接入节点管理、日志管理、关系图谱）与必须保留的项（地名搜索／路网分析／要素查询这种直接对应功能点的词，删了会被判响应不全），末尾给一句「要分条风格我再出分条版」。
4. **量化锂点不动**：7 条产业链、71 项标准、全 40 集这类数字是识别度来源，压字数不删数字。

实测压缩比（原文→成稿）：349→124、367→146/127、230→143/111、202→144/125、398→152/139 字。

- 单项文字控制在 100 字左右，用户会明确要求「缩减到100字左右」；写长了要主动收。
- 用户说「不用发word版，直接给我文字即可」时，只在对话里给文字，不生成 docx。
- 评价标准不能只堆性能指标，必须融合功能要求（如「门户建成后应包括开放目录、数据图谱…等功能，并形成电脑端和移动端双端访问」）+ 性能指标两部分。
- 地名/机构名被脱敏成「某」时，写「跨区域」等中性表述，不替用户猜具体地名。

## 五、从初设取数的实操要点

- 初设 docx 极长（约 38,000 段、166 个表格），标题用 Word 自动编号，正文里搜不到「5.2」「9.5.2」这类编号，必须按 `p.style.name == 'Heading 3'` 遍历还原层级。
- **标题有重名**（如「项目建设目标」出现两次），用 `dict(name -> index)` 会覆盖错位并抛 KeyError；正确做法是先 dump 全部 Heading 3 的段落索引，再用 `(start, next_start)` 区间切片取正文。
- 性能与安全量化指标在 4.6.2 性能需求分析：用户层（含各门户）活跃并发 ≥200、查询类接口 ≥150TPS（1 次接口调用计 1 个事务）、简单查询 P95 ≤2 秒、复杂统计查询 P95 ≤8 秒、首屏可交互 P95 ≤2 秒；互联网区部署 SSLVPN 安全网关与 SSL 证书，密码采用国密算法。
- 开放门户 = 9.5.2（含电脑端、移动端 H5、智能问数助手；数据要素×大赛是其同级兄弟节，不算门户本体）。
- 「标准规范」= 9.2：，编制 **71 项**标准规范及配套制度/指南/规程，覆盖总体建设、数据资源管理、数据治理、共享应用、安全管理、运行保障六大方面；原则是「急用先行、分类推进，成熟一批、发布一批」；15 项重点标准（数据元、数据库设计、元数据、数据质量、自然人/法人基础库、共享交换、数据回流、数据服务接口、数据级联、登记、脱敏、分类分级）。
- 「商密改造」在初设里对应 9.11 密码应用方案 / 9.12 密码应用方案的密评，**正文只有「详见附件」**——三段得自己拼：4.7.2 密码应用合规要求（《密码法》、GB/T 39786-2021、GB/T 43206-2023）、4.7.2 传输/存储加密条款（国密 SSL/TLS + SM2/SM3/SM4、SM4 落盘）、9.13 密码资源池与商用密码产品认证证书要求（国家密码管理局商用密码检测中心签发、有效期内）；评价标准落到「通过密评 + 国密算法全覆盖 + 产品证书有效 + 由云服务商提供密码能力的须明确能力边界并通过等保三级」。
- 团队月报模板是六段式：收入利润目标差异及完成计划／应收账款完成情况／五融推进情况／重点产品重点商机及规模以上收入项目进展／年底集成收入攻坚项目进展／其他重点工作事项；陕西智慧民政与四川省数字政府两个项目都放「年底集成收入攻坚项目进展」。
