# OCR 布局噪声（`<|LOC_n|>`）污染与恢复实录

**日期**：2026-10-01 发现 / 启动恢复
**规模**：102 篇笔记受影响，其中 73 篇有效文本 <30%

---

## 一、现象

月度巡检报「无标签 27 篇 / 无摘要 24 篇」，但逐篇看下去发现问题更深：
这些文件的 **tags 是垃圾**（`小时代`、`护理`、`Fred M`、`晴`），因为它们是**从垃圾正文生成的**。

打开正文看到满屏 `<|LOC_471|>` 这类标记：

| 文件 | 正文长度 | `<|LOC_` 处数 | 去噪后 | 有效占比 |
|---|---|---|---|---|
| `19.《数据安全技术-数据安全风险评估方法》` | 149,479 | 11,572 | 19,256 | **12.9%** |
| `102.《中国企业数据资产入表情况跟踪报告》2024年度报告` | 488,658 | 37,307 | — | 16.2% |
| `2.《企业数据治理实践自皮书》` | 582,370 | 43,694 | — | 18.0% |
| `3.《人工智能治理案例集》` | 1,937,339 | 140,640 | — | 19.7% |
| `81.《中国数据交易场所业务规则汇编（2025年版）》` | 2,121,307 | 154,258 | — | 20.3% |

最坏的文件去噪后**剩下的还是多语言乱码**（藏文/西里尔/随机拉丁），说明那次 OCR **整体跑废**，不是单纯多打了标记。

---

## 二、根因：别怪当前 prompt，是 2026-08 那次老引擎

诊断顺序很重要——**先证伪"当前引擎有问题"再往下查**。

### 1. 先验当前 prompt（结论：干净）

对同一页 PDF，用百炼 `qwen-vl-ocr-latest` 跑三种 prompt，统计 `<|LOC_` 出现次数：

| prompt | 输出 | LOC 噪声 |
|---|---|---|
| `请提取图片中所有文字，保持原文段落结构。只输出文字，不要加解释。` | 2,062 字 | **0** |
| `Text Recognition:` | 2,080 字 | **0** |
| `Document Parsing:` | 3,828 字（带 JSON/HTML 结构） | **0** |

→ 现行引擎**不会**产生 `<|LOC_`。

### 2. 再查历史来源（结论：老引擎）

`<|LOC_n|>` 是 **PaddleOCR-VL（硅基流动）的布局特殊 token**。
grep 全库拿到了关键证据：**61 篇正文带这个标记行**：

```
> **云端OCR(PaddleOCR-VL)重跑**：2026-08-03 13:25（正文 88 页）
```

即 2026-08-01~03 那次 `re_ocr_cloud.py` 全量重跑（当时 skill 明确指引「统一用云端 PaddleOCR-VL」）
是污染源。**那条旧指引已在 SKILL.md 里改正**，见「扫描件 PDF 大批量入库」节。

### 3. 顺便证伪的假设

- **mtime 不可用**：`note_enhance` 会重写文件，mtime 全被刷新，看不出年代（污染文件和干净文件都集中在 2026-08）
- **不是当前 prompt 的模式问题**：三种 prompt 都 0 噪声
- **不是 lint 报的"无标签"本身**：那是下游症状，不是根因

## 三、恢复管线

### 步骤 1 — 清点与分档

```bash
cd /opt/data && uv run --with pyyaml python3 \
  skills/productivity/knowledge-base-maintenance/scripts/vault_lint_dump.py
```

再单独扫噪声：对每个 md 统计 `count('<|LOC_')` 和
`有效占比 = len(re.sub(r'<\|LOC_\d+\|>','',body)) / len(body)`，按 <30% / 30-60% / >60% 分档。
**注意统计范围只算 frontmatter 之后的正文**，否则 frontmatter 长度会稀释比例。

汇总成 `/opt/data/.tmp_tests/ocr_noise.json`（file / loc / body / clean / ratio）。

### 步骤 2 — 映射源 PDF

从 md 头部的 `> **原始文件**：xxx.pdf` 行取文件名，与 `WebChat BackUp/文档/**/*.pdf` 建索引匹配：

```python
import glob, os
pdfs = {os.path.basename(p): p
        for p in glob.glob('/opt/data/WebChat BackUp/文档/**/*.pdf', recursive=True)}
```

用 `pymupdf` 读页数。实测 **65/102 能定位源 PDF**，37 篇源文件已不在（只能去噪）。

### 步骤 3 — 重 OCR（百炼 qwen-vl-ocr）

关键参数（实测得出，照抄）：

| 参数 | 值 | 说明 |
|---|---|---|
| 模型 | `qwen-vl-ocr-latest` | 百炼 `compatible-mode/v1/chat/completions` |
| prompt | `请提取图片中所有文字，保持原文段落结构。只输出文字，不要加解释。` | 三种 prompt 实测都 0 噪声；用这个保留段落结构 |
| 渲染 | `dpi=150` 的 PNG，base64 | 渲染本身很快（0.13s/页），不是瓶颈 |
| **并发** | **8** | 实测 1.36 页/s。**并发 16 无收益**（1.27 页/s），别盲目加 |
| max_tokens | 6000 | 留够大文档单页 |
| 重试 | 429 时 `sleep(6*(att+1))`，共 5 次 | 实测全绿，没触发过 |
| 断点续传 | 每文件写完即落 `reocr_done.json` | 必须；长任务不可重跑 |

**吞吐实测（重要）**：

| 文件 | 页数 | 耗时 | 吞吐 |
|---|---|---|---|
| 第 1 篇（冷启动） | 22 | 161s | 0.14 页/s |
| 第 2 篇 | 88 | 103s | 0.85 页/s |
| 第 3 篇 | 35 | 31s | 1.13 页/s |

→ **别用首篇估 ETA**，首个文件有连接/冷启动开销。稳定后 0.85–1.36 页/s。
10463 页 ≈ **2–4 小时**。先跑 1 个文件量吞吐，再给用户报 ETA。

写入格式（保持与既有 OCR 文件一致，便于以后 grep 识别）：

```
# <title>

> **原始文件**：<pdf 文件名>
> **云端OCR(qwen-vl-ocr)重跑**：2026-10-01 21:04（正文 22 页）
---

<body>
```

**不写 frontmatter** —— 留给下一步 `note_enhance` 生成。

### 步骤 4 — 阶段 A：源 PDF 缺失的只去噪

```python
raw = re.sub(r'<\|LOC_\d+\|>', '', s)
raw = re.sub(r'\n{3,}', '\n\n', raw)
raw = re.sub(r'[ \t]{2,}', ' ', raw)
```

并在 `---` 前插一行留痕，便于以后区分「已尽力去噪」和「还没动过」：

```
> **已剥离OCR布局标记**：2026-10-01 21:30（源 PDF 缺失，内容未恢复）
```

**不要假装这算修好了** —— 内容没恢复，标签仍会是垃圾，交付时要说明。

### 步骤 5 — 阶段 B：全部重跑 note_enhance

正文换了，旧 tags/summary/related **全部过期**，必须重跑：

```python
subprocess.run([sys.executable, '/opt/data/note_enhance.py', path], timeout=600, cwd='/opt/data')
```

每 8 个 `sleep 4` 退避。批量前**先单文件验证**（见 SKILL.md 的验证方法），
确认输出 `✅ 摘要: 5条要点 / ✅ 标签: 10个`；看到 `🛑` 或 `❌ 0条` 立刻停。

### 步骤 6 — 阶段 C：复检 + 前后对比

重跑 lint，与月度巡检报告做对比表（断链 / 无frontmatter / 无标签 / 无摘要 / 标签不足 / 孤立），
标注剩余项属于「边缘态」。用户要看数字，不要只说"修完了"。

## 四、附带发现

1. **`<|LOC_n|>` 也出现在正文之外的地方**：`related` 里会出现由噪声派生的幽灵链接
   （如 `[[数据资产入表咨询、课程培训:陈阳17301209296]]`）——那是**源 PDF 里嵌的硬广告行**
   （`数据资产入表项目咨询、首席数据官课程培训:陈阳…(同微信)`）被 OCR 吸进正文后又被 LLM 当成笔记名。
   重 OCR 后广告行依然会在（它是源文件的真实内容），**不要批量删**，但要知道它的存在。
2. **防御**：`pdf_ocr.py` 已在 `_post()` 出口加 `_sanitize_ocr()`，任何引擎的输出都统一剥
   `<|LOC_\d+\|>` 并打印清理条数——即使将来兜底引擎再被命中也不会污染入库。
