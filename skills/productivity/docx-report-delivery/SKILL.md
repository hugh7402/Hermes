# docx 报告生成与交付

已验证工作流（2026-08-22 智慧民政 7-8 月月度重点项目汇报材料）。

## 模板复制法（格式100%一致）

目标：新 docx 与上期文件格式完全一致。**不要从头排版**，直接复制上期文件做模板。

步骤：
1. `shutil.copy(上期.docx, 新路径)`
2. python-docx 打开，先分析并 `copy.deepcopy` 关键段落元素：
   - 标题段、信息段（团队名称/汇报时间）、章节标题段、正文段（首行缩进）、编号段（无缩进）
3. 删除 body 里所有 `w:p`（**必须保留 `w:sectPr`**）
4. 按内容结构循环 `copy.deepcopy` 对应段落元素插入，set_text 只改第一个 run 的 `w:t`、删除多余 run
5. 验证（无 soffice 时）：python-docx 重开查段落数/字号；markitdown 读回查内容完整

已知格式规格（6月智慧民政汇报材料，可类推）：
- 标题 18pt（size=228600 EMU）粗体居中
- 团队名称/汇报时间 10pt（127000 EMU）居中
- 章节标题 = Heading 2（一、二、…六、）
- 正文首行缩进 first_indent=279400 EMU（≈22pt）
- 编号段（"1. xxx"）无缩进，编号是手打文本、非自动编号

## 月度汇报内容组织（团队月度会汇报材料）

**模板随期更换：先读当期模板的六个标题再动笔，不要套上期的结构。** 已见两版：

- **现行版（团队月度会汇报材料）**：一、收入利润目标差异及完成计划｜二、应收账款完成情况｜三、五融推进情况｜四、重点产品、重点商机及规模以上收入项目进展｜五、年底集成收入攻坚项目进展｜六、其他重点工作事项。
  格式规格：标题仿宋 **15pt 粗体居中**；正文仿宋 **12pt**、行距 1.2、段前 6pt/段后 6pt、首行缩进 24pt；六个章节标题仿宋 12pt 加粗、段前 15pt；信息行「团队名称：…　汇报人：…」「汇报时间：2026年M月」。
- 历史版（7-8 月、9 月沿用）：重点业务产品打造｜重点项目攻坚与落地成果｜商机拓展与储备转化｜现存问题卡点与风险｜工作计划与攻坚举措｜其他事项。

数据源 → 章节映射（现行版）：
- **一/二/三（收入利润、应收账款、五融）只有财务口径，项目材料里拿不到** → 一律写【待补】，并在稿后编号列出要用户补的每一项。
- **五、年底集成收入攻坚项目进展** ← 用户点名要写进月报的项目都放这一节（如陕西智慧民政二期、某省数字政府投标项目），每个项目按「总体进度／建设成效／运营实效／主要卡点／攻坚举措」分小节，不要写成流水账。
- 陕西民政的进度数字 ← 最新一期**双周工作汇报**；运营实效 ← **项目月度报告**（账号、登录次数、点击量、共享/归集数据量、各板块业务量）。
- 四、重点产品（2 个）← 团队实际在交付的产品线；**商机名称/金额/阶段、规模以上项目的合同额与本年收入确认 ← 须向用户要**。
- 六、其他 ← 标准与专利、方法工具沉淀，其余待补。

**口径冲突处理**：双周报与项目月度报告的时间点天然不同（双周报可能报 278 项/完成 160/58%，项目月度报告同期仍写 262 项/150/57%）。
**进度类取最新一期双周报，运营类用项目月度报告并显式标注「截至 9 月底」** —— 两个口径不要混在一句里，也不要把旧口径当最新报出去；交稿时说明取了哪个口径。

## 月度汇报内容组织（历史版，仅供旧期复刻）

数据源 → 章节映射：
- 一/二/四/五 ← 最新一期**双周工作汇报**（建设推进口径：任务总数、当期完成率、累计进度、延期构成、重点工作、问题与建议）
- 平台运行数据（账号数、登录次数、点击量、共享/归集数据量）← 知识库 `concepts/陕西省智慧民政…月度报告…md`
- 三、商机 ← 双周汇报一般没有，**须向用户要**（上期内容：农资监管平台调研、村社区系统建设建议书、蚂蚁集团/医保住建对标/捐赠系统对接）
- 六、其他，以及三在无数据时 → **保持空标题**，与上期体例一致，不要编造

**缺数据纪律**：缺什么（当月商机、平台运行数据、上一双周结束后的最新进展）**列成清单向用户要**，不要拿上期数字顶替、不要编造。

占位符的处理分两种情形，别搞反：
- **数据在项目材料里拿得到** → 写实；某一节确实无数据（如商机）→ **留空标题**，与上期体例一致，成品里不留占位符。
- **用户只给了模板、没给经营数据**（收入/利润/应收/五融这类只有财务口径的数字）→ 照模板出**完整初稿**：能写实的章节（项目进展、重点产品、其他事项）写实，缺数的位置写
  【待补：具体缺什么口径】；交付时在稿后**编号列出需要补的每一项数据**。宁可交带【待补】的稿子，也不要空等数据或编数字。

**先找脚本再动手**：`/opt/data/scripts/gen_report_docx.py` 是 7-8 月版的生成脚本，改 `content` 列表就能出下一期。用户明确说过“之前都有脚本，不用新写”——先搜已有脚本。

### 初设/投标文档的「三段式条目」（建设内容/应用场景/评价标准）

写这类条目（或核查别人填的分工表）时先读 `references/bid-doc-three-part-items.md`。两条硬约束先记在这里：
**每个方面就一段话、约 100 字，编号改成并列句**；**评价标准必须“功能要求 + 性能指标”各占一半**
（只给性能数字会被打回），指标取原文数字，不自己造口径。

### 在用户新给的模板上就地填充（稀疏模板首选）

用户发来一个只有六个空标题的新模板时，**不要清空 body 重建**（那是复刻已有成品的做法），直接**在标题后面插入正文段**：
先用 python-docx 摸清模板格式（字体/字号/对齐/行距/段前后，注意 `section.*_margin` 可能是 `None`，
打印时 `f'{v.mm:.1f}' if v else 'None'` 免得 AttributeError），再把内容逐段插到对应标题之后。

关键三点：
1. **按标题倒序插入** —— 拿到标题段落列表后 `for p, key in reversed(targets)` 依次插；正序插会让后面标题的段落对象错位。
2. **深拷贝标题段再改成常规体** —— `copy.deepcopy(anchor._p)` + `anchor._p.addnext(new_p)`，删掉所有 run 后 `add_run(text)`，
   再统一设 `仿宋`（`rPr.rFonts.set(qn('w:eastAsia'), '仿宋')`）、12pt、行距 1.2、段前段后 6pt、首行缩进 24pt。
3. **删掉模板自带的填写提示语** —— 模板里常有 "1-2 个重点产品，" "重点商机 / 项目，规模以上收入项目（控制不超过 5 个）" 这类说明文字，
   那是给你的指令不是正文，成品里必须删干净（按前缀匹配删段）。
4. **用户说“整合”就把分条并成 1-2 段** —— 他原话要求过「把这几条文字内容整合，形成 1-2 段话，不用再标序号」：
   把 `1. 2. 3.` 改写成连贯段落（「…方面，一是…二是…」），【待补】要**内嵌到句子里**，不要留成独立占位段。
   没要求整合的章节仍用「1. 2. 3.」分条（历史版体例）。

输出目录沿用 `OutPut Box/团队月度重点项目汇报材料_<YYYY年M月>/`，文件名优先沿用模板原名 + 月份
（如 `XXXX团队10月月度会汇报材料_2026年10月.docx`），不要在模板名后面另起一套叫法。

骨架脚本：`scripts/fill_docx_template_inplace.py`（模板路径 + 标题→段落列表的 JSON 即出稿，自带提示语清理与回读校验）。

**改生成脚本时别原地覆盖**：`write_file` 对「本轮没读过全文」的已有脚本会拒写，直接另存 `…_v2.py` 再跑
（或先 `read_file` 读全文再覆盖），比反复试写省回合。每版脚本都从同一份模板与内容源重新生成，成品才幂等。

### 读双周汇报 PDF：先过滤表格行

markitdown 转换双周汇报 PDF 时，横排表格行与正文交错输出，正文被 `|` 行切碎（只剩约 1/6，容易误以为内容缺失）。过滤后再读：

```python
lines = [l.strip() for l in t.split('\n')]
body = [l for l in lines if not (l.startswith('|') or l.startswith('---'))]
# 再滤掉纯数字行（页码）和空行
```

附件任务明细表单独按 `|` 行解析：责任处室、责任人、计划日期、"已延期"标记 → 统计延期构成与下一双周节点。

### 交付后校验

```bash
export PATH=/opt/data/.venv/bin:$PATH
python3 /opt/data/skills/productivity/docx/scripts/docx_validate.py <out.docx>   # 期望 {"ok": true, "issues": []}
python3 -c "from markitdown import MarkItDown; print(MarkItDown().convert('<out.docx>').text_content[:800])"
```

再打印每段 style + 字号，确认格式继承成功（18.0pt 标题 / 10.0pt 信息行 / Heading 2 章节 / 编号正文）。

详见 `references/monthly-team-report-workflow.md`（章节映射、已产出记录、复用脚本骨架）。

## 个人绩效类汇报（季度/年度重点工作完成情况）

**触发**：用户一句带全部要求，如"编制我的三季度重点工作完成情况，结合年度岗位责任书、部门总监及副职临时交办的任务，突出成效，300字以内"。
**与团队汇报的区别**：数据源不是项目报告，而是**年度岗位责任书 + 本人经手的任务**。

### 动笔前必须拿到三样（缺就别写）

1. **年度岗位责任书** —— 考核基线。常见结构是「指标 × 时间节点」，通常一半带 6月底／12月底两个节点；
   先拆成「指标 N ｜ 年底目标 ｜ 半年节点」三列再动笔。
2. **本季度任务清单**（正式任务）。⚠️ 平台导出的往往是**真 BIFF `.xls`**（文件名常带 `todoListExport_`），
   **markitdown / openpyxl 都读不了**（openpyxl 只认 xlsx，会报格式错），要用 **`xlrd`**：
   `xlrd.open_workbook(p)` → `sh.row_values(i)`。读完先**按日期筛出本期**再统计条目数
   （2026-10-11 实测：99 条总记录 → 三季度 47 条、其中工作类 32 条）。
   **写进正文的每个数字都要能当场说出「从哪筛出来的」** —— 用户会核对出处（"这是你总结的吗"）。
3. **总监／部门副职临时交办的任务** —— ⚠️ **这类往往不在任何任务表里**，但恰恰是考核"听指挥、能挑事"的部分；
   **必须主动提醒用户补，不问就漏**。

> 知识库里通常**没有**《岗位责任书》和本季度总结（2026-10-10 实测两份都没找到）；先穷尽检索，
> 再把缺口**列成清单向用户要**，不要拿上期数字顶替、不要编。

### 口径：对准**年底**目标，不对准半年节点

责任书两个节点里「12月底前」才是年度考核口径。**季度总结要对着年底目标说进展** ——
三季度是攻坚期，写成"半年节点已完成"会让三季度显得没推进，年底考核吃亏。

### 素材还原路径（用户没给清单时的兜底）

1. 搜 **岗位责任书／责任人清单／年度工作方案** —— 本人岗位定位常在《…建设推进工作方案》的
   **附件责任人清单**里（实测从"联系人员：杨杉（咨询规划）、邵雷（架构师）、侯涛（交付）"定位到本人角色）；
   责任人清单附件本身可能只是空标题（markitdown 把表格吃掉了）→ **去正文的工作方案里找**。
2. 本季度的**双周／月度汇报** —— 取项目口径数字（任务总数、当期完成率、累计进度、延期构成、平台运行量）。
3. **本人本季发来的文件**（微信落盘 `/opt/data/cache/documents/` + 知识库 `01-WeiXin/`）——
   最能反映他真正经手了什么；知识库文件的 mtime 不可靠（批量导入会全刷成同一天）。
4. 挂不上责任书指标的活儿 → **单独归入"其他重点工作"，不硬塞**。

### 写作硬要求（用户偏好）

- **300 字以内**（个人总结；团队汇报 500–800 字）——字数按**含标点**算（比"不含标点"更严，先满足它），
  交付时把**含标点 / 不含标点 / 汉字数**三个都报出来让用户自己核；**标题不计入正文**，正文另计。
  工具：`scripts/todo_export_digest.py --count 草稿.txt`
- **见事见数**：每项成果带具体事项 + 量化数据
- 动词用 **主导／牵头／推动／独立完成／支撑**，不用"参与／协助／完成"流水账；
  但**没主导的不许写"牵头"** —— 只参会/只对接的写"参与／对接"，虚报会在追问时露底
- **突出成效**：先说成果再说做法（"成果获 X 认可"之类前置，再提做法）
- 去 AI 味：套话、空洞拔高、结尾展望全删（humanizer 清单）
- **小标题直接用责任书的指标名**（"一、重点项目支撑。二、新行业突破。三、规划与标准。"）——
  评审一眼看到对应关系，别自己另起一套说法
- 详细配方与检索命令见 `references/performance-summary-sources.md`

### ⚠️ 交付顺序：先给成稿，缺口列在稿子后面

**不要把提问当交付。** 2026-10-11 实测：我先回了一版稿子但**以三个问题开篇**，
用户直接重发了一遍原请求（"请结合我的年度岗位责任书，编写一版…"）——他要的是稿子。

正确顺序：**成稿（可直接粘贴）→ 编排逻辑说明 → 缺口与风险（放最后，编号列出）**。
该我判断的（哪些算"临时交办"、涉密工作怎么写）**先按最合理的方式写好，再在稿后点明我的假设**，
不要停下来等确认。

### 交付形态

工作汇报类走 **一版成型**（不先出提纲，用户看结果再调）：微信发正文，同时存一份 docx 到 OutPut Box。

**用户明说「不用发 word 版／直接给我文字」时就只给文字**，不要再附 docx —— 他要粘回别人（甲方/上级）的文档里，
文件反而碍事；同理，只是几段话的小改动、又要他复制粘贴的，默认给正文文字，除非他点名要文件。

**个人绩效类 docx 用公文格式**（没有上期模板可复刻时）：`templates/gongwen_docx_spec.json`
直接喂给 `docx/scripts/docx_create.py` —— A4 公文页边距（上37/下35/左28/右26mm）、标题黑体 18pt 居中、
正文仿宋_GB2312 14pt、首行缩进 28pt（=2 字符）、1.5 倍行距。
出完必查 `docx_validate.py`（期望 `{"ok": true}`）+ markitdown 回读关键句仍在；
**发送前 `cp` 到无空格的 `/opt/data/…` 路径**（OutPut Box 带空格会让 MEDIA 路径截断）。

⚠️ **涉密／涉投标的活儿要不要写进这类总结，先问用户，不要自行决定** ——
写不点名的泛化表述、还是完全不提，是用户的判断，不是我的。

## 长文生成的模型陷阱：正文会「静默为空」（2026-10-10 实测）

写方案/汇报这类长文时，**模型名与 max_tokens 配错会静默产出空文档** —— 接口 HTTP 200、
脚本不报错、`content` 却是空字符串，最终写出一个只有标题的 docx。交付前必查三项：

1. **先列账户里到底有哪些模型**，别照抄文档里的模型名：
   `GET https://api.deepseek.com/v1/models` —— DeepSeek 官方实测只有 **`deepseek-flash` / `deepseek-v4-pro`**，
   **没有 `deepseek-chat`**（老笔记里的 `deepseek-chat` 已失效）。
2. **推理型模型的 `reasoning_content` 与正文共用 completion 预算** —— 给少了，推理吃光预算 → 正文为空。
   实测：`deepseek-flash` 写 200 字正文烧掉 3733 completion token；`deepseek-v4-pro` 写 2260 字正文
   耗时 34s、completion 3274。**max_tokens 从 16000 起步，长文给 24000。**
3. **两道闸门（缺任一道就会静默写空文件）**：

```python
content = (resp['choices'][0]['message'] or {}).get('content') or ''
if not content.strip():                  # 闸门 1：推理吃光预算的静默失败
    mt = min(mt * 2, 32000); raise RuntimeError(f'模型未返回正文，mt→{mt} 后重试')
if resp['choices'][0].get('finish_reason') == 'length':   # 闸门 2：被截断
    mt = min(mt * 2, 32000); raise RuntimeError(f'输出被截断，mt→{mt} 后重试')
```

三轮用尽就抛错，**绝不返回空串**。

⚠️ **生成后必须回读校验**：`docx_validate.py` 只查包健康（zip/部件/图片字节），**查不出空正文**。
必须再用 markitdown 读回确认关键句还在（见「交付后校验」），然后才交付。

⚠️ 换模型/换供应商前**先请示用户**（用户定的规矩：效果第一、性价比第二、换模型须用户同意）。
建议先实测一条最小请求（列出模型 + 跑一次长文），把耗时与 token 数报出来再定。

## 微信文件投递

- chat_id 从 `/opt/data/channel_directory.json` 的 `platforms.weixin[].id` 取（如 `o9cq807-...@im.wechat`）
- 用 cron 一次性任务（agent 会话内无 send_message 工具）：
  `cronjob(action="create", name=..., prompt="将文件 <绝对路径> 作为附件投递给当前微信用户（用文件投递能力发送，不要只发路径文本）", schedule="1m", deliver="weixin:<chat_id>")`
- 验证：`cronjob(action="list")` 看该 job 的 last_status=ok、last_delivery_error=null、state=completed
- 限流兜底：iLink rate limited 会导致投递失败（cron last_delivery_error 可见 "rate limited"）；文件同时放 OutPut Box 目录并告知用户路径，用户可自行取
- **MEDIA 路径不能含空格** ⚠️：`MEDIA:/opt/data/OutPut Box/xxx.docx` 里的空格会让路径被截断、文件发不出去。发送前先 `cp` 到无空格路径（如 `/opt/data/<文件名>.docx`），再在回复里写 `MEDIA:/opt/data/<文件名>.docx`
- 在线会话直接在回复里用 `MEDIA:<绝对路径>` 比 cron 快（cron 适合定时/离线投递）；两种方式交付后都要确认用户确实收到

## 终端守卫坑（lifecycle_guard embedded null bug）

terminal 执行 python 脚本时，命令中可执行路径含 `/`（如 `.venv/bin/python3`）会触发 `ValueError: open: embedded null character in path`——守卫把含 `/` 的可执行 token 当被引用脚本，读 ELF 二进制内容（NUL 保留）后递归扫描崩溃。

绕法：先 `export PATH=/opt/data/.venv/bin:$PATH`，命令用**裸命令名** `python3`（不含 `/`）。

注意：execute_code 沙箱没有项目依赖（docx 等），别指望它替代。
