# 初设/投标文档的「三段式条目」撰写与核查

用于：从初步设计方案里提炼「1.建设内容 2.应用场景 3.评价标准」三类条目，
或批量核查各系统负责人填的「系统 / 建设内容 / 应用场景 / 评价标准」表。
（来源：某省一体化数据资源管理系统初设 9.5/9.6 各子系统、系统建设内容分工表、68 条问题反馈表）

## 一、从初设 docx 里定位条目

1. **章节号在正文里搜不到**：初设的标题多是自动编号，正文文本里没有「5.2」字样。
   先按 `Heading 1/2/3` 层级还原编号（`h1.h2.h3` 计数器），再按用户说的号找到对应标题的**段落索引区间**
   （`[起点, 下一个同级或更高级标题)`），不要靠 grep 章节号。
2. **抓三样就够写 100 字**：该节的「系统设计/系统概述」首段（含系统定位与功能清单）、
   Heading 4「建设内容」下的一级模块名、以及原文里的量化锚点（“共包含 15 个一级功能模块…合计 3911 项功能”）。
   几千段的巨节（数据编目、一数一源、决策支撑、应用服务）也只需这三样，不要去读全文。
3. **性能指标另取一处**：性能类数字在「性能需求分析」节（并发 ≥200、接口 ≥150TPS、简单查询 P95 ≤2s、
   复杂统计 P95 ≤8s、首屏 P95 ≤2s），密码类在密码应用/密评节（GB/T 39786-2021、SM2/SM3/SM4、
   商用密码产品认证证书、通过密评）。写「评价标准」时把它们引过来，**不要自己造口径**。
4. **脱敏地名不猜**：原文用「某」代替合作方地名时，写「跨区域」，不要替用户猜成具体省市。

## 二、写作规格（用户明确要求，反复纠正过）

- **每个方面就一段话，约 100 字**（汉字 95–130 可接受）。用户连续两次说“文字太多了”，
  把 398 字的四条编号压到 124 字才通过 —— **默认就按 100 字写**，别等他砍。
- **编号必须转成并列句**：`1、2、3、4` → 「提供 A（…）、B（…）、C（…）等能力」，
  细项收进括号或直接删；不要交一条条编号的清单。
- **评价标准 = 功能要求 + 性能指标，两者缺一不可**。只写性能指标会被直接打回：
  用户原话「评价标准不对，你更多给的是性能指标，应该还有一部分功能要求」。正确骨架：
  > 「门户建成后应包括开放目录、数据图谱、开放指数…等功能，为个人、机构提供数据开放服务，
  > 并形成电脑端和移动端双端访问；同时满足并发用户不低于 200、查询接口吞吐不低于 150TPS，
  > 简单查询 P95 不超过 2 秒、复杂统计查询 P95 不超过 8 秒的性能要求。」
  即：**前半句功能验收（列出必备模块与端），后半句性能验收（原文数字）**。
- 交付时把每段**字数报出来**（X 汉字 / Y 字符），用户会核。
- 用户说“不用发 word/直接给文字”就只回正文，不附文件。

## 三、批量核查别人的填写（xlsx 分工表）

1. **先定模板行**：用户会指定「库仓类照『X基础库』、系统类照『Y系统』」，把这两行的三栏抄下来当基准。
2. **逐行机械校验**（脚本化，别目测）：字数是否偏离模板、库仓类评价标准是否缺量化指标
   （归集率 100% / 校验率·覆盖率 100% / 更新率 99% / 质量达标率 90%）、
   系统类评价标准是否缺「测评 / 上线条件」、建设内容是否缺「以X为基础·整合多部门·归集治理·支撑行业应用」四要素、
   应用场景是否缺「高效办成一件事 + 市（州）属地化 + 核验/查询接口/库表同步」三要素。
3. **备注列的写法跟随用户自己的风格**：他手写的几条一般是**编号 + 问题 + 处置动作**（如「1.评价标准缺（测评、上线条件）条目」「2.去掉性能要求」「3.建设内容文字精简合并」），
   不写长篇解释、不加“请按模板补写”这类尾巴。先读他填的那几行，再照同一句式补其余行；**他填过的行原样保留，不要覆盖**。
4. 备注列设浅黄底 + 自动换行 + 列宽 60–80，无问题的行留空，方便他筛。

## 四、常见坑

- 用户说“按照之前的要求”＝沿用上一次的格式契约（一段话/约 100 字/不编号），不是重新商量风格。
- 同一节里“对接方式 / 归集方式 / 访问方式”会分三次改名 —— 以最新那条为准，
  并且**只改用户点名的那个位置**（`div#fi-dock > label`），同一页的其他同名字段保持原样。
- 表格里出现重复的中文字段（如两个「归集方式」）时，先分清哪个是下拉标签、哪个是只读回显，再决定改哪个。
