# 政务项目分期工作计划编制

用户给出一个工作簿：内含「指标成效」（分期目标）、一个「…（示例）」sheet（颗粒度参考）、若干空的待填 sheet。任务是编制任务分解计划并填进待填 sheet。

## When to Use

- 用户说「编制成效详细计划」「把计划填进 xx sheet」「按指标成效排任务」；
- 收到含「指标成效」+「（示例）」sheet 的工作簿，里面还有空白的待填 sheet；
- 要给政务项目（专题库 / 标准规范 / 基础库 / 平台建设）出带责任岗位、起止日期、时长、交付物的任务分解表；
- 已有初设或验收指标文件，要把分期目标反向拆成可执行的周级任务。

不适用：纯文本方案撰写走 `plan-writer`；通用 Excel 读写走 `xlsx`；领导驾驶舱 / 作战图走 `excel-driven-dashboard`。

## 🚨 四条铁律

### 1. 计划跟着「指标成效」的分期节点走，不跟着填表窗口走

先把「指标成效」每一列读出来（典型三列：2026 年底阶段成效目标 / 次年 2 月初验 / 次年 5 月终验），把**待编对象的当期目标逐条抄下来**。
每个 sheet 的阶段划分 = 指标成效的阶段划分，阶段名直接写成「阶段一收口（2026年底）」「初验阶段（2027年2月初验）」「终验阶段（2027年5月终验）」，让表格自己能对上指标。

> 反例（被用户否掉的）：把 71 条标准的起草+内审全压进 12-30 前的 47 天窗口。用户原话是要看见「12 月 30 日前只完成 7 类技术规范，整个编制持续到次年 2 月」——**指标只考 7 类，就不该在首期把另外 22 条也排完**。

### 2. 先算工作量装不装得进窗口，再动手排

从清单取每项人月，乘条数得总量，除以窗口工作日得**所需并行人数**。
- 所需并行人数明显超出合理团队规模 → 必须分期，不许硬排。
- 实测：71 条 × 1.2 人月 = 85.2 人月 ÷ 47 天窗口 ≈ 需 56 人满负荷并行。这个数字是分期方案最有力的依据。
- **把这个数主动报给用户**，并说明「15/12 个编制组并行」是排期隐含前提——他对这个前提有异议，整条时间轴都要重排。

### 3. 颗粒度照抄同簿的示例 sheet，不要自己发明

逐项抄它的：工作分类维度与顺序、工作细项粒度（典型 ≤3 天一句一个动作）、责任岗位命名口径、交付物写法、**工作分类列的纵向合并**写法、表头配色与日期格式（`yyyy/mm/dd`）。
新表的列宽、字体、边框也照抄，用户会直接把两张表贴进同一份汇报。

### 4. 当期只承诺当期交付物

后续阶段的场景/能力写「为后续……预留支撑」「预留分析基础」，不要写成已支撑。把初验、终验的能力写进首期任务描述，评审会当场指出。

## 步骤

1. **读源簿**：`openpyxl` 列出全部 sheet 及行列数；**注意旧版 `.xls` 清单要用 `xlrd` 读**，不要试图转换。
2. **抄指标成效**：把每个待编对象的三期目标原文抓出来，逐条列出「要求关键词」（如六个环节名、指标名、百分比），后面对表用。
3. **定分期与并行度**：按期目标反推每个阶段要完成哪些条目；按铁律 2 算并行组数。
4. **写生成器，不要手填**：把「屏/条目定义（数据表）」与「写入格式（样式函数）」分开，改口径只需改数据表重跑。
5. **跑校验**（见下），通过后再交付。

## 校验清单（每次必跑，程序化，不靠眼看）

- **日期越界**：所有开始/结束都落在声明的窗口内
- **时长自洽**：`结束 − 开始 + 1 == 时长（天）`
- **清单零缺失**：拿清单里的名称集合减表里出现过的名称集合，差集必须为空（程序化比对，不靠肉眼扫 150 行）
- **指标覆盖**：指标成效要求的关键词逐个 `in` 全文拼接，全中才算过
- **原始 sheet 未被改动**：示例页、指标成效页的行列数与首行内容前后一致
- **禁用词**：产物里不出现「演示/投标/原型/采购需求」这类词

## 🚨 常见坑

- **阶段偏移量基准不统一，三个阶段会叠进第一个月**。各阶段任务常按「相对本阶段起点」写偏移，若落日期时统一用阶段一基准，初验/终验的任务全部会挤到当月，且**表面看不出错**（日期都合法、时长也对）——只能靠「按阶段统计起止范围」发现。写完必须分阶段打印 `min(开始) → max(结束)` 核对。
- **偏移量别用工作日推**：示例 sheet 的日期是**连续自然日**（含周末），照它的口径走日历日，别自作聪明跳周末，否则天数对不上示例的观感。
- **清单条目一律不许自己新增**。清单里缺某类（如指标要「授权运营」但 71 条里 0 条），**先问用户**：新增一条、扩写现有某条覆盖、还是先标注缺口。自增会让预算和工作量口径对不上。
- **每人月都是同一个值时，要点出来**。71 条全写 1.2 人月 / 2.4 万元，那是按条数均摊的占位值，不是逐条估算。照它排期自洽（都按 3-5 天起草），但**要提醒用户可改按难度分档**（重档 5-7 天 / 中档 3-5 天 / 轻档 2-3 天），由他决定。
- **汇总行/合计列**：清单若有「工作量小计 / 单价 / 费用合计」，交付时把总量算出来报给用户（条数 × 人月、金额），他会拿去对预算。
- **示例页通篇是 `·` 占位**：那是用户自己的占位符，不是空值错误，**别去清洗或改成空**。
- **用户会重发同一份源文件**（有时连发两次以上，或分两次发不同 sheet 的文件）。收到后先 `sha256sum` 比对已入库副本：**一致就明说「源文件未变，计划无需重做」并直接给已有成品**，不要因为又收到一次就重建一版。不一致才重做，并先问清哪一版为准。
- **用户会追问「这是原文还是你总结的」**。任务细项里的能力表述要能在初设/指标文件里找到依据，不要为了通顺改写措辞。
