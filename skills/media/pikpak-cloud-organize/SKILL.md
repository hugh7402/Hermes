# PikPak 云盘大目录批量整理

> 实测：`/Pack From Shared` 1642 文件夹 / 9495 文件 / 10149 GB → 802 文件夹 / 5305 文件 / **845.95 GB**
> （删 4190 文件 / 9303 GB，耗时 <2 分钟；全程进回收站可恢复）

## 五个致命坑（不踩才能做对）

### 1️⃣ 文件名重复 ≠ 内容重复（最危险）
`1.mp4` 在 79 个不同剧集文件夹里各有一份，`第二集.mp4` 53 份 —— 它们是**不同短剧各自的第1/2集**。
按文件名全局去重会删掉几十部不同剧。**必须用 `(文件名, 字节数)` 二元组判定重复**。

### 2️⃣ 无扩展名/畸形命名的文件往往是视频
实测 17 个「非视频」实为视频，按一刀切会误删：

| 形态 | 例子 |
|---|---|
| 丢了点 | `第6集mp4`、`娘子与郎君 第一集mp4`、`禁忌之门第二集` |
| 点后有空格 | `第2集. mp4` |
| 纯集号 | `1~4集`、`5~8集`、`9~12集`、`EP2`、`秘密教学第1-5集` |

判定函数：正常扩展名 ∈ VID_EXT，**或** 正则 `(第\s*\d+\s*集|\d+\s*[~\-～]\s*\d+\s*集|^EP\s*\d+|^\d+\s*集|第[一二三四五六七八九十]+集)$`，**或** `[^.\s](mp4|mov|avi|mkv)$`。

### 3️⃣ 尺寸交叉验证：API 与 WebDAV 都要查
PikPak 对超大包（.tar）会报出 TB 级尺寸（实测单文件 3,971,514,109,952 字节 = 3.6TB）。
**不要想当然认定是假尺寸** —— 用 `rclone lsl 'pikpak:<目录>'` 交叉验证，两者一致即为真实占用。

### 4️⃣ 推广包的识别特征
同一站点分享包会在**每个剧集文件夹里塞同一份推广包**（诱导付费/加群）：
- 特征：`(文件名, 大小)` 完全相同，且出现 ✅ **≥3 个不同父目录**
- 实测样本：`精彩后续点击这里.tar` ×213（6.44GB）、`自购合集.tar` ×9（226.6GB）、
  `资源持续更新中，别错过.zip` ×22（7.28GB）、`更多精彩内容点这里.URL` ×58
- 仅出现 1-2 次的压缩包是**唯一内容包**（可能是独有内容），务必单独列出让用户决定

### 5️⃣ 限流与异步
- `delete_to_trash(ids)` 返回 `{'task_id': ...}` —— **异步任务**，不是同步删除
- 批量操作会触发 `The number of tasks in transmission has reached the limit, please try again later.`
- **对策**：批量间隔 0.3-1s；遇限流退避 60s×(n+1) 重试（实测等 90s 即恢复）
- 单批建议 20-40 个 id

## 标准流程

### 第1步：递归清点（必须落 JSON）
用 `pikpakapi` 递归遍历，分页拉全（`next_page_token` 循环），每条记录：
`{id, name, path, kind, size, depth, phase}` → 写 JSON，**后续全靠这份快照做计划**。

⚠️ 需经 bash wrapper 运行：
```bash
bash -c 'cd /opt/data && export PATH=/opt/data/.venv/bin:$PATH && python3 .tmp_tests/xxx.py'
```

### 第2步：分类与计划（不执行）
1. `is_video_name()` 分出视频 / 非视频（含上面的畸形命名兜底）
2. 非视频 → 删（按用户指令；**`.bif` 是蓝光缩略图索引可删，`.m2ts` 是主视频必留**）
3. `(名,大小)` 跨目录重复 → 保留 1 份
   - **保留哪份**：所在目录文件数最多者（避免剧集被打散）；同分→路径短者→字典序
4. 同目录同 stem 不同扩展名 → 留体积大的（清晰度高）
5. 输出待删清单 JSON + 分类汇总（数量/体积）

### 第3步：空文件夹清理
删完非视频后大量目录变空壳（实测 831/1642）。
生成 `nonempty` 集合时**必须把文件的全部祖先目录都加入**，否则父目录会被误判为空。
按 `depth` **倒序**删除（深的先删）。

### 第5步：多合集「打散 + 按剧名归一化」（大工程，实测可行）

多个大合集内容重叠时的彻底整理（实测：4 个合集 648 个单元 → 559 个剧集，
695 文件 845.95 GB 零丢失，耗时 ~22 分钟）。

**核心思路：单元 = 直接含视频的目录**，把单元搬到新容器，用归一化名合并。

**关键实现细节（都是踩过的坑）：**

| 坑 | 正确做法 |
|---|---|
| 建目录 | `create_folder(name, parent_id=…)` → 返回 `{'file': {'id': …}}` |
| 搬目录 | 搬**整个单元文件夹**（`file_batch_move([dir_id], to_parent_id=…)`），不要逐文件搬 —— 648 次 vs 4866 次 |
| ⚠️ **多套一层的坑** | 归一化改名时**不要「新建干净名目录 + 把原目录塞进去」** —— 会产生 `剧名/原目录名/文件` 的多余一层（实测 483/583 个中招）。正确做法：**把原目录移入容器后用 `file_rename` 改名为干净名** |
| 压平已产生的嵌套 | `剧集/唯一子目录/文件` → 把子目录的内容 `file_batch_move` 到剧集目录，再删空子目录（实测 483 个，831s，0 失败） |
| 归一化过狠 | `^[A-Za-z]\d*[\s\-_]*` 会把 `AV女优生存指南` 削成 `v女优生存指南` —— **必须要求后面跟 `-`/`_` 才算编号前缀** |
| 把真剧名当分类名 | 别把「出现 ≥3 次的同名」当成通用分类去按父目录区分 —— 那正是要合并的对象！通用分类名得手工白名单 |
| 跳过已存在同名 | `if nm not in cont` 会把「与容器内完全同名的重复目录」直接跳过，必须先处理同名合并再处理新归入 |
| 散片 | 合集根下的散落视频，按文件 stem 各建一个文件夹（stem 碰车 → 并入已存在的同名文件夹） |
| 内容分类 | 别把网黄/同人/动漫全倒进「短剧」容器 —— 按路径关键词分流到多个容器 |

**建议的最终形态**（顶层从 ~600 项压到个位数）：
```
Pack From Shared/
  短剧（归一化）/          ← 扁平化，一剧一文件夹
  同人动漫（归一化）/
  网黄网红（归一化）/
  芃芃大人/               ← 个人创作者合集，整体保留
  动漫/                    ← 番剧，整体保留
  啄木鸟 25部 （9）/        ← 厂牌套装，整体保留
```

**验证口径**：合并前后必须核对**文件总数与总体积完全一致**（实测 5305 / 845.95 GB 前后不变）。
⚠️ 文件夹数量会**变多**（802 → 1195）—— 因为扁平化后目录变浅，原来的 `depth < 4` 递归限制不再截断。别把这个当异常。

### 第6步：同名剧集合并- 候选：同名目录出现 ≥2 次
- **排除父子嵌套**：若 `path[i+1].startswith(path[i] + '/')` 则跳过（那是嵌套不是重复）
- **选主目录必须按「子树文件数」**（`sum(1 for f in files if f.path.startswith(dp+'/'))`），
  不是直接子文件数 —— 否则会选到只有子目录、自己 0 文件的那份
- 移动：`file_batch_move(ids, to_parent_id=主目录id)`（⚠️ 参数名是 `to_parent_id`，不是 `parent_id`）
- 重名冲突：同为文件且同大小 → 直接进回收站；否则 `file_rename(id, 名 + ' (2).ext')` 后移动
- 移完复查源目录，空了就删
- **重试脚本要以实时 `file_list` 为准（幂等）**，不要用旧快照 —— 部分成功的批次会跑偏

## 跨位置去重（云端 vs 本地）

场景：已经把一部分下到本地，要把云端的重复副本删掉。（实测：本地 1130 文件/218.6GB vs 云端 5305/845.9GB
→ 判出 308 个重复 / 89.54GB，删后云端 4997 文件/756.41GB）

### ⚠️ 关键陷阱：通用名会造成交叉积假信号
本地与云端各有十几个 `1.mp4`/`2.mp4`/`第二集.mp4`，
按“同名不同大小”枚举会得到 **2622 对** 垃圾对比 —— 全是 `2.mp4` 相互组合。

**正确做法：只看「字节数相同」，再用三重打分定稿**

| 信号 | 分 |
|---|---|
| 文件名完全相同 | +2 |
| 文件名归一化后相同（剥 `2048.hk@`/`x3f3.com `/后缀） | +2 |
| 父目录名完全相同 | +1 |
| 父目录名近似（一方包含另一方，或中文/英文 token 重合度 ≥50%） | +1 |

**得分 ≥2 才判为重复**（仅字节数相同不算）。实测 308 个命中里 253 个是满分 3。

### 为什么不能只靠文件名
云端/本地路径结构完全不同（云端已归一化、本地是旧目录），
所以「父目录名相似度」是关键补充信号。例：
- 本地 `夜伴灵姬/2.mp4` ↔ 云端 `短剧（归一化）/夜伴灵姬/2.mp4`（同名+同目录，行）
- 本地 `2048.hk@《重生之征服郭伯母》第八集.mp4` ↔ 云端 `.../第八集.mp4`（名不同但字节数+父目录对上）

### 顺序
1. 先按**字节数**建索引（云端 size → [文件]），只比对同字节数的候选
2. 打分 → 每个云端 id 只保留最高分的那条（避免一文件匹配多条）
3. 删云端（`delete_to_trash`）
4. **删完再扫一遍容器，把删空的剧集目录也删掉**（实测 308 个文件删完 → 27 个剧集目录变空）

## 有用 API 速查
```python
c.file_list(parent_id=pid, next_page_token=…)   # 分页列目录
c.delete_to_trash(ids)                          # 进回收站（可恢复）
c.delete_forever(ids)                           # 永久删（慎用）
c.file_batch_move(ids, to_parent_id=pid)        # 批量移动（⚠️ 不是 parent_id）
c.file_rename(id, new_name)                     # 重命名
c.create_folder(name, parent_id=pid)            # 建目录 → ['file']['id']
c.untrash(ids)                                  # 从回收站恢复
```
令牌：`/opt/data/.pikpak_token.json`（字段 encoded_token/access_token/refresh_token/user_id/device_id）

## 汇报口径
务必给出「清理前 → 清理后」的**文件数 + 体积**对照，并说明：
- 走的是**回收站**（可恢复），不是永久删除
- 删了什么类别、各多少
- 保护了哪些容易误删的（畸形命名视频、唯一内容包）
- 日志文件路径
