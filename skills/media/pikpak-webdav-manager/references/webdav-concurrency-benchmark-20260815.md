# WebDAV 并发基准测试（2026-08-15）

## 背景
用户要求找出 WebDAV 并发下载的最优并发数（最大速度 + 稳定）。用 PikPak WebDAV（dav.mypikpak.com）实测。

## 测试方法
- 工具：`/tmp/rclone copy pikpak:<路径> <本地> --buffer-size=128M --multi-thread-streams=0`
- 测试文件：My Pornhub 内 200-500MB 视频（8 个）
- 每级并发：每个文件独立 rclone 进程，跑 15-30s，按落盘字节数计算速度
- 预热 5-10s 后采样，避免启动延迟污染数据

| 并发 | 速度 |
|:----:|:----:|
| 10 | 81.1 MB/s |
| 12 | 92.0 MB/s |
| **15** | **111.2 MB/s（峰值）** |

### 15 并发稳定性验证（5×5s 采样）
采样：111.9 / 103.6 / 93.2 / 78.6 / 90.6 → 平均 **95.6 MB/s**，波动 33.3 MB/s（可接受）

## 结论
- **最优并发 = 15**：峰值 111MB/s，稳定 79-112MB/s，平均 95.6
- 20 并发开始饱和下降（82MB/s）——服务器/带宽上限
- 单文件 5-8MB/s，多文件并发**线性叠加**（每个文件独立连接）
- 小文件（<500MB）速度快，大文件（GB 级）握手慢但稳定

## 实战验证
Inbox-JAV 批量下载（6 个文件 66GB，JUR-341 27GB 等）：
- `rclone copy pikpak:Inbox-JAV <本地> --files-from 列表 --transfers 15 --buffer-size=128M --multi-thread-streams=0`
- 实测 94.5 MB/s，与基准峰值吻合

## 关键教训：误判"卡死"
- 症状：8 个 rclone 进程 CPU 5-13%、无 443 连接、无输出 → 误判卡死
- 真相：**大文件 WebDAV 握手慢**（40s+ 无连接无输出），实际一直在下载（.partial 文件增长）
- **正确判断方法**：看目录里 `<文件名>.<8位随机>.partial` 文件是否存在且大小增长 = 正在下载
- 误判代价：杀掉正常下载进程，浪费已下载的 28GB

  - WebDAV 下载 → moov atom not found
  - 重下（rclone 退出码 0）→ 仍损坏
  - CDN 直链 aria2 下载 → 仍损坏（333MB 满大小但 moov 缺失）
  - **判定：PikPak 源文件本身损坏**（不是下载问题）——WebDAV + CDN 双通道都损坏才能实锤
  - 处理：删本地坏文件 + 删 PikPak 源（避免未来误下载），无法修复除非换磁链

### 字幕重命名（用户纠正，下载后必须做）
- 字幕文件名必须与视频文件名一致（同名同目录）
- 按番号匹配：`re.match(r'([A-Za-z]{2,6}-?\d+)', name)` → 大写去连字符后配对
- 例：`DLDSS-348.[4K]@R.srt` → `DLDSS-348-入田真綾-...幼儿教师.srt`
- 无匹配视频的字幕保留不动（如 EBWH-342-U 残留）
- 本次 7 个字幕改名成功

### 删 PikPak 源文件（用户纠正，下载验证后必须做）
- 只删本地存在且大小≥99% 的文件，保留未下载的/文件夹（如怪奇物语字幕）
- delete_to_trash 后列表有缓存延迟（立即 file_list 可能仍显示旧项），**需重新查询一次确认真正清空**
- Inbox-JAV：13 个源删干净；My Pornhub：17 个源 + 1 个损坏源全删

### 大批量删源（400+ 文件，2026-08-15 AI短剧）
- delete_to_trash 单次最多约 20 个 id，**必须分批**（20/批 + 0.3s sleep），否则可能超时/失败
- 递归收集云端文件时同时比对本地（本地存在且大小≥99% → 入删除清单；否则保留）
- AI短剧 408 个源 21 批删完，根级剩 49 项（本地没有的小文件/图片保留在云端合理）
- 删除前先确认：本地视频总量 vs 云端清单——`云端有但本地无` 的才是真正要补下的（对比时注意去 `2048.hk@` 前缀，云端带网站前缀而本地可能已去前缀）
