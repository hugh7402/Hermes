术语和定义
数据模型 data model
一种用于描述数据结构和数据之间关系的抽象模型，它定义了数据的存储方式、组织结构以及数据之间的关系。
[参考来源：《数据管理术语标准》]
概念模型 conceptual model
概念模型是数据建模的第一阶段，它通过对业务对象的抽象与合并，以数据的方式来描述对象的高级概念和对象之间的关系，而不涉及具体的技术实现细节。
[参考来源：《数据管理术语标准》]
逻辑模型 logical model
逻辑模型是数据建模过程中的一种抽象表示，它描述了数据之间的结构、关系和约束，但不涉及具体的物理实现细节。逻辑模型通常用于数据库设计阶段，作为概念模型向物理模型的过渡。在逻辑模型中，实体、属性和关系被定义得更为具体，但仍然与具体的数据库平台无关。
[参考来源：《数据管理术语标准》]
物理模型 physical model
物理模型是逻辑模型的具体实现，它定义数据在数据库中的具体存储方式，包括索引、存储结构、分区等细节。
[参考来源：《数据管理术语标准》]
主题域 subject domain
主题域是企业级数据中划分出的互不重叠的数据分类，每个主题域定义了特定的数据边界，并管辖着一组密切相关的业务对象。通常同一主题域有相同的数据所有者。
[参考来源：《数据管理术语标准》]
业务对象business object
业务对象是指业务领域中重要的人、事、物对象。业务对象承载了业务运行和管理中涉及的重要信息，是信息架构中最重要的管理要素。
[参考来源：《数据管理术语标准》]
逻辑实体 logical entity
逻辑实体是指在数据建模中，代表现实世界关键对象或概念的抽象元素，具有明确的边界和业务含义。逻辑实体是数据库设计的基础构成单元。
[参考来源：《数据管理术语标准》]
属性 attribute
属性是用于客观描述业务对象在某方面的性质和特征，是信息管理的最小粒度。逻辑实体中属性的物理展现为表、视图、文档、图形或文件中的列、字段、标记或节点等。
[参考来源：《数据管理术语标准》]
数据模型设计原则
完整性原则
在充分参考各类业界企业级数据模型的基础上，结合集团公司实际情况，确保模型包含了正确的、全面的业务概念，涵盖现有业务范畴及数据范围。其中涉及的重要实体、重要关系、重要分析维度等属性应保持完整。
继承性原则
指数据模型要遵循已有的概念，即所建立的模型应该在已存在主题的基础上进行细化。确保数据模型的全局一致，并保障数据可溯源，逐步形成企业统一数据模型。
可扩展性原则
主题分类应具有高度的通用性，支持业务规则的多变性，保持数据模型的动态调整能力，以适应复杂的业务情况，并为后续拓展新的业务提供一定程度的技术支持。
连贯性原则
模型中的数据与数据之间应有连贯性，由于单独的数据所体现的价值往往比相关联的数据少，数据间的连贯性可充分发挥数据的分析价值。
前瞻性原则
应从业务的未来发展趋势看待模型，除了支持现有的业务与数据需求外，设计出来的模型应能够适应企业未来的业务发展，以支撑行业先进概念与企业未来需求。
可操作性原则
模型的应用可与日常操作和实例快速结合使用，易于让业务人员理解和使用，有助于指导业务系统研发。
数据模型设计规范
主题域模型设计
集团公司各部门、各单位协助数信中心梳理集团公司现有业务，通过前期调研，形成企业级数据域划分，包含L1数据主题域分组、L2主题域。
数据模型设计
业务系统数据模型由集团公司各部门、各单位主导建设，梳理归属领域业务，参照业务系统建模方法，结合本单位实际业务，进行业务系统数据建模。业务系统数据建模中通常将数据模型分为概念数据模型、逻辑数据模型、物理数据模型三个层次。这三个层次从抽象到具体，逐步实现从业务需求、数据结构到技术落地的转化。L3级业务对象作为业务领域中可操作、可识别的关键实体，通过连接业务与数据，直接决定了数据模型能否真正支撑业务决策和价值挖掘。
以L2级征地移民域下属的L3级居民户为例，业务系统数据模型构建过程如下：
明确业务对象
居民户这一业务对象在移民征地域中是确定性较高的业务范畴，涉及到对居民户相关信息的管理和处理,是所有征地移民业务场景（如补偿测算、安置规划、政策执行、风险防控）的“数据锚点”。其对业务分析的意义体现在精准支撑业务决策、确保政策落地公平性、提升资源调配效率等多个关键环节。
梳理关键实体与属性
针对居民户这一业务对象，梳理出相关的关键实体，如人口信息表（L4逻辑实体），并进一步细化人口信息表的属性（L5属性），包括主键ID（用于唯一标识每条记录）、户ID（关联户的信息）、姓名（居民个体标识）、曾用名等。通过对这些属性的梳理，形成了关于居民户这一业务对象的分域数据视图，该视图详细描述了居民户相关数据的具体构成和组织方式。

属性规范与约束描述
属性规范与约束包括定义属性规则、指定域、指定键、制定属性规范等。
首先定义具体属性的规则，如唯一性约束、外键约束。指定域是指同一业务域下实体属性的格式和数值应保持一致。指定键是指实体的属性可以是键属性，也可以是非键属性，需要指明主键、外键等信息。
属性制定遵循三个渐进式范式。
第一范式（1NF）：表的每一列都是原子的（不可再分的最小数据单元），每一行都是唯一的（通常通过一个主键来保证），列的顺序和行的顺序无关紧要。
第二范式（2NF）：表必须首先满足1NF，所有非主键列都必须完全依赖于整个主键。如果表的主键是复合主键（由多个列组成），则任何非主键列不能只依赖于主键的一部分。
第三范式（3NF）：表必须首先满足2NF，所有非主键列之间不能存在传递依赖。

逻辑模型在概念模型的基础上进行细化和转换，如实体转换为表，属性转换为字段。根据图4-4模型创建相关实体表，设置部门编码、部门名称等字段。
物理模型设计
物理数据模型是逻辑模型在计算机中的具体表示，描述了数据在物理存储介质上的组织结构。通过定义数据类型、存储引擎、分区策略、索引、压缩方式等技术细节，实现逻辑模型可落地、数据可高效存储与查询的目标。建立物理模型的方法和步骤如下：
表结构设计
将逻辑模型中的实体、属性、关系转换为数据库中的表、列、主键、外键等结构。例如逻辑实体中的人口户信息表，包含了户籍号、户主身份证号、户类型、登记日期、所属派出所、联系电话等属性，其中户籍号为该逻辑实体的唯一标识，户主身份证号对应人口信息表的主键，可以用来关联两表。由此可以确定表名为人口户信息表，户籍号为主键，户主身份证号为外键，户类型、登记日期、所属派出所、联系电话等为表中其他字段。详设阶段，业务建设方需提供字段名、数据类型、是否主键、是否外键、非空约束、默认值、是否自增、字段注释等信息，用以确定表结构并生成建表语句。
存储优化
根据数据的特点和访问模式，优化数据的存储方式和访问路径。
对于非结构化数据，要根据数据的“访问热度”和“性能需求”，选择不同存储介质并分层部署，实现成本与性能的平衡，如需高频访问的数据，采用SSD（固态硬盘）或高性能对象存储；访问频率中等（如近 3 个月的业务文档、历史日志），采用SAS 硬盘或低成本对象存储；极少访问（如归档的历史视频、过期日志），采用SATA 硬盘、磁带库或归档存储。
对于非结构化数据的“海量性”远超单节点存储能力，需采用分布式架构实现横向扩展，将数据分片存储在多节点，通过 “副本机制” 保证可用性，通过 “负载均衡” 提升数据读写性能。
对于文本类数据，可采用Gzip（压缩率高，适合冷数据）、Snappy（压缩 / 解压速度快，适合热数据）、ZSTD（平衡压缩率和速度）等压缩算法；对于图片、音频、视频等文件，可针对重要性采用不同的编码格式存储（如JPEG、WebP、MP3、H.265等），降低存储成本。
模型实现
物理模型是将逻辑模型转化为适配数据库的存储结构，需兼顾查询性能、存储效率和可维护性。建设过程需从技术选型、逻辑映射、分区索引设计到性能优化逐步推进，在数据库中创建相应的表、索引、视图等对象，并导入数据。
索引设计
为表中的关键字段设计索引，以提高查询性能。
数据管理平台模型（数据仓库）设计
业务系统数据模型建设完成后，应在数据管理平台的进行注册并统一管理。注册成功的模型将作为源端系统数据核查的依据。
数据管理平台模型建设需从业务视角出发结合需求进行主题域组与主题域归集，按照维度建模方法进行数据仓库设计。
建模规范要求
1.共性需求提炼
建立跨主题域的公共业务对象矩阵，识别共享属性（如ID、基础属性、状态标签），构建公共数据集；
核心模型与扩展模型分离：核心模型支持通用业务逻辑，扩展模型处理个性化需求。
2.命名规则
（1）数据分层
结合数据分层原则，各层命名如下：
贴源层：ODS
明细层：DWD
汇总层：DWS
应用层：ADS
（2）主题域
在数据仓库中，可以将不同的业务领域划分为不同的主题域。主题域的命名应为单一单词缩写或多单词首字母缩写。数据分域及命名情况详见附录1。
（3）数据库
所有数据库名称应为“前缀_单一单词或多单词首字母缩写_后缀”，数据库名称尽可能简短易懂。
前缀：数据分层层级。
贴源层：ODS_主题域分组；
明细层：DWD_主题域分组；
汇总层：DWS_主题域分组；
应用层：ADS_主题域分组；
后缀：数据库环境；
测试库：_TEST；
生产库：无。
例如ODS_HRD_TEST（人资域贴源层测试库）
（4）维度表
前缀规则‌：以DIM或DIM_开头，标识为维度表。 ‌
‌结构‌：DIM_主题域_维度类型_自定义标签，例如DIM_FINANCIAL_AREA（财务板块区域维度表）。‌
（5）指标表
前缀规则‌：指标表位于ADS层，指标表命名增加ADS_为前缀，后接指标名称和数据分区。 ‌
‌命名结构‌：采用“ADS_KPI_业务域_关键字_分区”的组合
例如ADS_KPI_PERM_CAPITAL_INVESTMENT_YEAR_2025。其中，指标名称严格遵循《指标库》中的内容。
（6）标签表
标签表位于ADS层，标签表命名增加ADS_为前缀。
命名结构‌：通常以ADS_TAG或ADS_TAG_开头，后接业务域和标签类型，例如ADS_TAG_FINANCIAL_ACCOUNTING（财务核算标签表）。
‌扩展规则‌：若涉及多维度组合，可采用ADS_TAG_业务域_标签类型结构，如ADS_TAG_ENGINEERING_QUALITY（工程质量标签表）。
（7）实体表
实际业务使用的表，为规范管理，统一命名规范。
ODS层表名称应是“数据分层_业务系统名称/缩写_业务系统表名_数据更新周期”。例如，ODS_USERSYS_USERINFO_D（贴源层用户数据实体表，来源UserSys系统的UserInfo表，按天更新），业务系统名称参见附录2
DWD/DWS层表名称应是“数据分层_主题域_表主题_数据更新周期_后缀”。
例如DWD/DWS_FINANCIAL_ACCOUNTING_H（数仓层财务域，财务核算表）。
其中，表名均采用大写英文字母。
后缀：
历史表。存储系统历史信息的表。以“_HIS”作为后缀； 
配置表。存储系统配置信息的表。以“_CFG” 作为后缀； 
日志表。存储系统日志信息的表。以“_LOG” 作为后缀； 
中间表。ETL过程中为方便数据处理，创建中间过渡的表。以“_MID” 作为后缀； 
备份表。用于数据备份的表。以“_BAK” 作为后缀； 
测试表。用于数据测试的表。以“_TEST” 作为后缀；
事实表。正式业务使用的表。没有内容做后缀。
（8）临时表
测试或临时处理手动创建的表，为方便管理，统一命名规范，临时表名称应是 前缀+表名+分区 的字段名。
前缀：TMP_
后缀：_分区
例如：TMP_FINANCIAL_ACCOUNTING_YEAR_2025（2025年度财务核算临时表）
（9）编码表
所有代码表数据实体命名均以CODE_开头。表名称应是前缀+表名+分区 的字段名
前缀：CODE_
后缀：_分区
例如：CODE_EQUIPMENTINFO_YEAR_2025（2025年度设备信息代码表）
（10）表索引
命名规则：前缀：IDX_。
索引名称应是 前缀+表名+构成的字段名。如果复合索引的构成字段较多，则只包含第一个字段，并添加序号。
例如：IDX_T_DW_EQUIP_EQUIPMENTINFO_H_EQUIPTID（DW层设备域设备信息表中项目ID字段的索引，IDX_为前缀，DW_EQUIP_EQUIPMENTINFO_H为表名，EQUIPTID为构成字段）。
（11）表键值
主键命名规则：
前缀：PK_。
例: PK_DEPT_1 ;如果表名过长可以使用缩写形式
外键命名规则：
前缀：FK_。
例: FK_DEPT_1；如果表名过长可以使用缩写形式。
（12）视图
前缀：V_。按业务操作命名视图，参考实体表规范。
（13）存储过程
前缀：PROC_。
存储过程名应是 前缀+目标表+业务操作名。
例：PROC_TDUB_DEPT_Update。
（14）函数命名
函数命名规则：
前缀：F_。
例：F_TRAN_AREA

SQL开发规范
1.SQL长度规范
SQL代码不能超过50000个字节（包括注释），代码行数不能超过1000行，union all关键字不能超过50个
2.表查询关联语句规范
SQL编码时，对于分区表需要先按照分区字段以及其他筛选条件资源做过滤，筛选后在与其他表做关联查询。
错误样例：
SELECT
	t1.id,
	t1.name,
	t2.id AS id_b
FROM
	(
	SELECT
		a.id,
		a.name,
		a.address
	FROM
		a) t1
LEFT JOIN (
	SELECT
		b.id,
		b.name,
		b.address
	FROM
		b) t2 ON
	t1.id = t2.id
WHERE
	t1.month_id = '202512'
	AND t1.day_id = '10';

正确样例：
SELECT
	t1.id,
	t1.name,
	t2.id AS id_b
FROM
	(
	SELECT
		a.id,
		a.name,
		a.address
	FROM
		a
	WHERE
		a.month_id = '202512'
		AND a.day_id = '10') t1
LEFT JOIN (
	SELECT
		b.id,
		b.name,
		b.address
	FROM
		b
	WHERE
		b.month_id = '202512'
		AND b.day_id = '10') t2 ON
	t1.id = t2.id
3.SQL编码规范
为方便数据血缘解析，以下为编码规范：
SQL代码中应用到的所有关键字、保留字都使用大写，且不要缩写，如select、from、where、and、or、union、insert、delete、group、having、count等。
SQL代码中应用到的除关键字、保留字之外的代码，都使用小写，如字段名、表别名等。
四个空格为一个缩进量，所有的缩进皆为一个缩进量的整数倍，按代码层次对齐。
禁止使用select * 操作，所有操作必须明确指定列名。
SQL查询结果中不能出现字段名重名，如果有重复字段必须使用as别名。
SQL中使用函数对字段进行操作时必须使用别名，如insert into table t1 select coalesce(name,’’) as newName from t2。
建表不可用create tableA as select * from tableB这种方式，要先建立表结构，再insert into tableA select * from tableB 
4.注释规范
每条SQL语句的注释单独成行、放在语句前面。
字段注释紧跟在字段后面。
应对不易理解的分支条件表达式加注释。
对重要的计算应说明其功能。
过长的函数实现，应将其语句按实现的功能分段加以概括性说明。
常量及变量注释时，应注释被保存值的含义（必须），合法取值的范围（可选）。
数据插入目标表时，最外层的SELECT后的字段要保留与目标表中文名一致的注释且不论字段名与目标表是否一致都应加上AS，其他查询不建议保留中文注释
5.字段排列规范
字段排列要求select语句选择的字段按每行一个字段方式编排。
select单独一行，字段换行二个缩进量开始。
每个字段前导二个缩进量，再在逗号后放置字段名。
两个字段之间的逗号分割符紧跟在第一个字段的后面。
as语句应与相应的字段在同一行。
6.SELECT字句排列规范
SELECT子句排列要求select语句中所用到的from、where、group by、having、order by、join、union等子句，需要遵循如下要求：
换行编写，与相应的select语句左对齐编排。
子句后续的代码离子句首字母二个缩进量起编写。
where子句下的逻辑判断符and、or等与where左对齐编排。
7.CASE语句格式规范
select语句中对字段值进行判断取值的操作将用到的case语句，对case语句编排作如下约定：
when子语在case语句的同一行并缩进一个缩进量后开始编写。
每个when子语一行编写，当然如果语句较长可换行编排。
case语句必须包含else子语，else子句与when子句对齐。
8.表别名定义规范
表别名定义约定所有的表都加上别名。在SELECT语句中给操作表定义了别名，在整个语句中对此表的引用都必须惯以别名替代。考虑到编写代码的方便性，约定别名尽量简单、简洁，同时避免使用关键字。
表别名采用简单字符命名，建议按a、b、c、d……的顺序进行命名。
多层次的嵌套子查询别名之前要体现层次关系，可用a、b、c、d来表示第一层次到第四层次；对于同一层次的多个子句，在字母后加1、2、3、4……区分。有需要的情况下对表别名加注释。
SQL查询结果中不能出现字段名重名，如果有重复字段必须使用as别名。
SQL中使用函数对字段进行操作时必须使用别名。
9.sql文件主题表加工数量限制
为方便后续运维，一个sql文件只允许对一张主题表的加工逻辑，不允许在同一个sql文件中进行两张及两张以上主题表的加工。
10.insert使用规范
为方便后续运维，一张表不论加工逻辑复杂与否，只能保留一个insert语句，不允许对一张表的多次插入操作。
11.连接使用规范
对于内连接和外连接的使用，要求该使用外连接的地方都已经使用了外连接，不需要外连接的地方一定不使用外连接。
表中的字段若是从其它表引用的，要确保该字段在被引用的表中存在。
不允许使用逗号“，”，要求所有的连接都写成JOIN的形式。
12.大小写规则
所有的SQL语句中的保留字均采用全部大写，不要使用缩写。如ALL AS CASE CREATE  DATABASE DELETE FROM IN INSERT JOIN LEFT NO NOT NULL SELECT TABLE UPDATE VIEW WHERE等。

模型加工开发安全规范
1.敏感数据加密处理
敏感数据主要包括
个人身份信息：
姓名、身份证号、住址、邮箱、银行账号等可直接识别个人身份的信息。 （手机号码暂时不考虑）‌
健康与医疗信息：
病历、诊断结果、用药记录、基因数据等涉及个人隐私的医疗健康数据。‌
金融账户信息：
银行账号、支付密码、征信报告、交易流水等金融相关敏感数据。‌
行踪轨迹信息：
实时位置、出行路线、住宿记录等可能暴露个人活动轨迹的数据。‌‌
2.敏感数据处理要求
敏感字段加密解密统一采用数据管理平台提供的国密SM4算法的ECB模式。

数据安全规范
为了保证数据的安全可控，对计划或准备实施入湖的数据、数据载体等，需要按照相关国家、行业、雅江集团的企业标准进行安全分类分级和敏感字段加密处理。
1.分类分级参考国家、行业、雅江集团相关标准；
2.敏感字段加密统一采用国密算法SM4_CBC_ENC，解密算法采用SM4_CBC_DEC。
