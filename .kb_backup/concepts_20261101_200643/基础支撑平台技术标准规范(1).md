引言
文档目的
为了使协同创新平台各业务应用充分了解如何实现与基础支撑平台进行接口对接，指导各业务应用完成与基础支撑平台集成工作。
预期读者
协同创新平台各业务应用管理人员及负责与基础支撑平台进行对接的技术人员。
基础支撑平台架构
协同创新平台的基础支撑平台部分将从六个方面为各业务应用平台提供基础支撑能力。主要包含统一门户、统一身份认证、统一消息中心、统一API网关、统一内容管理以及统一基础保障措施。在此基础上各业务应用需要完成以上系统的接口对接工作，来满足协同创新平台整体架构要求。

基础支撑平台接口思路
基础支撑平台在协同创新平台中起到重要的支撑作用，为各业务应用提供基础支撑服务能力。具体从统一门户、统一身份认证系统、统一消息中心、统一API管理平台等方面为各业务应用提供服务。
1、统一门户
协同创新门户作为平台的统一互联网出口，将对外汇聚展示需求主体、数商、创新主体、运营主体、监管单位等多方的征集需求信息、成果信息、活动运营信息。统一门户将集成平台各业务系统的数据接口，将数据实时展示到门户，同时也提供互联网申请表单和流程调度服务。
2、统一身份认证系统
统一身份认证系统实现了对各业务应用账户的统一管理以及权限的统一建立，通过统一认证与单点登录的建立，对业务应用的访问进行了整合，建立集中的认证管理机制。系统还实现了与京通、京办的集成对接，各业务应用无需再对接京通、京办，由统一身份认证系统实现用户数据打通、身份认证和单点登录服务，各业务应用均需要按照统一身份认证接口规范对接统一认证系统。
3、统一消息中心
统一消息中心作为基础支撑平台，实现了对各业务应用的通知、审批流程待办信息的集中管理。各业务应用依据集成规范，将待办信息及消息提醒与消息中心进行接口对接。同时还实现了与京办消息的集成对接。
4、统一API管理平台
统一API管理平台是API能力输出的载体平台，是API能力调用的入口平台，它的核心目的是满足API快速复用，它实现了API安全、稳定、统一、规范开放。

统一身份认证接口规范
简要概述
协同创新平台统一身份认证系统作为基础支撑平台，一是实现了各业务应用账号的集中管理，包括账号唯一标识生成，账号创建、修改、停用等全生命周期管理与账号数据同步；二是实现了密码认证方式的集中认证与单点登录。各业务系统须依据集成规范，一是完成账号对接，包括身份数据同步和账号梳理，实现各业务系统账号互联互通；二是完成认证和单点登录对接，实现一个账号一次登录多系统访问。
对接说明
统一身份管理平台以服务接口的形式实现与各业务应用的对接和交互，接口分为账号管理接口和统一认证集成接口两部分。通过旁路接入方式，对业务应用进行身份管理和统一认证的集成。认证服务接口基于OAuth2.1协议进行封装的REST接口。
认证流程（OAuth2.1模式）
业务应用调用接口时，判断用户未登陆（或未获取应用session）跳转登录页面，改为调用统一认证接接口时，无需考虑业务应用的认证和单点逻辑，由统一认证服务自行判断。

逻辑说明：
用户首先访问web应用，判断没有登录会话后进行redirect跳转，携带code_challenge跳转至统一认证服务界面；
用户在统一认证服务界面输入用户名和密码（或提交其它认证方式）进行授权确认后，由认证端进行redirect跳转回web应用；
web应用获得临时授权码，通过后台携带code和code_verifier调用获取token接口，获取授权Access Token；
web应用后台通过Access Token调用获取用户信息接口，获取用户信息。
web应用将用户信息写入会话，认证过程完成。

名词解释：
PKCE: PKCE 是 Proof Key for Code Exchange 的缩写，PKCE 是一种用于增强授权码模式安全性的方法，它可以防止恶意应用程序通过截获授权码和重定向 URI 来获得访问令牌。PKCE 通过将随机字符串（code_verifier）和其加密值（code_challenge）与授权请求一起发送，确保访问令牌只能由具有相应 code_verifier 的应用程序使用，保障用户的安全性。该模式是基于OAuth2.0的改进，是Oauth2.1标准的推荐模式。
code_verifier：在 [A-Z] / [a-z] / [0-9] / "-" / "." / "_" / "~" 范围内，生成 43-128 位的随机字符串。
code_challenge:经过相关加密的code_verifier
人员类型
自然人认证类型
L1-完成手机号码验证
L2-完成身份证件信息比对
L3-完成人脸识别认证或银行卡信息校验
法人认证类型
L1:法人单位、经办人实名，经办人未被授权。即未授权的口令账 
号、第三方办事账号。 
L2:法人单位、经办人实名，经办人已被授权。即已授权的口令账 
号、第三方办事账号。 
L3:法人单位、经办人实名，经办人已被授权，并获得数字证书。即 
一证通证书（介质版和移动版）、电子营业执照/电子印章。
接口准备
在统一身份系统中注册应用信息，提供必填信息包括应用名称、重定向（回调地址），以及非必填信息包括应用地址、推出地址、图标。信息提交成功后，系统会生成clientid和clientsecret用于后续oauth认证使用。

退出流程
目前统一认证平台支持统一退出，该操作指当用户在统一认证平台点击“退出”登陆后，统一认证平台会向应用发送退出指令（数据包），第三方应用的退出地址需要在平台“应用注册”中预先进行退出地址的注册，应用需要按照我们的要求构造接收并解析数据。
接收样例：
{"principal":"1","request":"logoutRequest","issueInstant":"2024-03-19T18:03:09.972Z","ticket":"AT-104-Sd3PHJ0WifsqEq7CPBx7mU4xM1EYdKqj","id":"2bd22df1-44d5-40cc-88dc-6ca5a31c3234"}

code有效期最大时间：120秒
token最大有效时间：43200秒=12小时

数据同步
用户数据推送需要第三方应用在统一身份系统中进行接口地址注册。统一身份认证系统会自动在接口地址后拼接 /user 的路由，以此为用户数据推送的完整地址，将用户信息推送到该地址。
接口准备
注册成功生成clientid和clientsecret用于后续数据推送时使用。推送数据均为SM4加密的json字符串，加密密钥为注册的clinetsercet。
加密
加密统一采用对称的国密sm4加密方式进行加密，使用clientSecret（第三方应用系统对接密钥）作为key，使用hutool自带的SmUtil进行加密。
解密
sm4作为一种对称加密算法，所以可以使用clientSecret作为key进行解密，解密实现方式如下，其中bcprov-jdk15on的版本请前往Maven中央库搜索，查找对应JDK的版本：
引入依赖：
	<dependency>
   		<groupId>cn.hutool</groupId>
   		<artifactId>hutool-all</artifactId>
   		<version>5.5.2</version>
	</dependency>
	<dependency>
   		<groupId>org.bouncycastle</groupId>
   		<artifactId>bcprov-jdk15on</artifactId>
   		<version>1.70</version>
	</dependency>
对密文进行解密：
	SymmetricCrypto symmetricCrypto = 		SmUtil.sm4(clientSecret.getBytes(StandardCharsets.UTF_8));
	String message_decrypt = symmetricCrypto.decryptStr(密文);
其中超16位的clientSecret取前16位作为加密key使用

主数据管理接口
简要概述
协同创新平台主数据管理作为基础支撑能力，一是实现了各类主数据信息集中管理，包括采集主数据表管理，采集主数据项的创建、修改、删除等；二是实现各类主数据信息对业务应用的分发使用。各业务应用需要依据接口规范，与数据管理中心主数据库进行对接，通过不同的主数据接口信息，获取人员、组织机构、场景、资源、工具等主数据进行使用。
人员、组织机构、角色通过统一身份认证系统获取,人员类型主要分为自然人、企业法人（经办人）、政府办公人员，组织机构大类分为自然人组、企业、政府单位，自然人组的人员会在之后的流程中进入到企业。具体对接方法见第4章。其他数据信息尚未确认，之后更新文档。
统一门户
简要概述
统一门户作为协同创新平台的基础支撑平台，一是作为互联网端统一入口，实现各业务数据的集中展示；二是实现了对各业务应用业务申请的集中入口。各业务应用依据集成规范，将展示数据进行接口对接。
统一API管理平台
简要概述
统一API管理平台作为协同创新平台的基础支撑平台，一是作为统一API管理平台是API能力输出的载体平台，是API能力调用的入口平台；二是实现了对协同创新平台南北流量的统一管理，提供了API的注册、鉴权和管控。各业务应用依据集成规范，将API接口注册到API管理平台中。

接口实施
接口对接主要工作内容为接口开发与联调测试。
接口开发：业务应用技术负责人与集成支撑平台技术负责人根据接口方案分别完成数据对接接口开发以及部署
接口联调测试：业务应用与与集成支撑平台进行测试数据调试，待测试成功后，上线试运行。
接口维护
维护阶段主要工作内容为更新维护与日常维护。
更新维护：业务应用和基础支撑平台如涉及对接模块有更新改造，及时联系对方对接负责人共同配合完成对接接口改造，保证业务正常运行。
日常维护：双方分别负责维护各自开发接口。保障业务正常办理、数据稳定交换。
设计规范
接口设计规范
项目中各系统接口统一采用RESTful API设计规范，接口调用均采用JSON格式进行数据传输。
RESTful API接口设计原则
1.资源定位
RESTful API接口应该通过URL来标识资源的位置，URL中使用标准的HTTP方法（GET、POST）和标准的HTTP状态码（200 操作成功、403 未授权和拒绝访问、404 找不到资源、500 操作失败等），禁止使用PUT和DELETE方法。
例如：GET /articles/1 表示获取ID为1的文章信息，POST /articles 表示创建一篇新的文章。
2.统一接口
RESTful API接口应该具有统一的接口，首先需要确定资源的URL和资源的请求方式，其次需要确定请求的参数和返回的格式。
例如：GET /articles?category=1&status=1 表示获取分类为1，状态为1的文章列表，返回JSON格式的数据。
3.无状态通信
RESTful API接口应该保持无状态通信，即每次请求都包含所有必要的信息，应用程序无需维护用户状态。
例如：用户每次请求API之前，需要通过OAuth认证或者Token认证获得访问权限，每次请求都需要添加Token等认证信息，避免请求与服务器之间的状态不同步。
RESTful API接口设计规范
1.资源命名
RESTful API接口中的资源应该使用名词作为资源名称，使用复数形式表示一组资源，使用短横线(-)作为单词之间的连接符。
例如：GET /articles 表示获取文章列表，GET /articles/1 表示获取ID为1的文章信息，POST /articles 表示创建新的文章。
2.响应格式
RESTful API接口应该使用JSON格式作为响应的数据格式，因为JSON格式比XML格式更节省带宽，解析速度更快，易于读写和理解。
例如：GET /articles 返回JSON格式的文章列表数据，GET /articles/1 返回JSON格式的ID为1的文章信息，POST /articles 返回JSON格式的新文章信息。
3.请求参数
RESTful API接口中的请求参数应该使用短横线(-)作为连接符，不使用下划线(_)或者驼峰式命名。
例如：GET /articles?category-id=1&status-code=1 表示获取分类ID为1，状态码为1的文章列表。
4.分页处理
RESTful API接口中的分页处理应该使用pageSize和pageNum两个参数，分别表示每页显示的记录数和从第几个记录开始显示。
例如：GET /articles?pageSize=10&pageNum=0 表示获取从第1个记录开始的10个记录。
5.异常处理
RESTful API接口中的异常处理应该使用标准的HTTP状态码和错误信息，以JSON格式返回给客户端，方便客户端进行错误处理。
例如：HTTP状态码为400表示客户端请求错误，HTTP状态码为401表示未经过身份验证，HTTP状态码为403表示服务器拒绝请求，HTTP状态码为404表示无法找到资源，HTTP状态码为500表示服务器内部错误。
安全要求
数据安全
为了实现数据安全，应建立数据备份和恢复机制，确保数据在意外情况下能够迅速恢复。同时，按照数据保密级别对应使用SM2、SM3等加密算法保护数据的存储和传输过程中的安全性也是必不可少的措施。此外，建立数据访问控制机制，确保只有经过授权的用户能够访问相关数据，也是数据安全规范的重要内容。在协同创新平台中，安全级别为三级及以上的数据不可出政务外网。
等保三级要求
项目等保级别为三级。
密评要求
统一集成对接密服平台。密码云业务服务是 PAAS 层提供业务服务的主要部分，提供签名服务和密钥管理服 务两部分，底层通过密码机实现安全计算，封装为 restful 接口，外部通过 http 协议请求其提供 restful 接口，进行相关的业务处理。接口包括：生成密钥对、PKCS1 签名接口、PKCS1 验签接口等。接口文档参见《首信云密服平台-MF接口说明V1.3.0》
