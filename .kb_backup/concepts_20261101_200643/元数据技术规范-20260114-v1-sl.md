前言
本文件参照《中国雅江集团有限公司数据管理办法（试行）》并结合元数据管理的业务需求起草。
本规范的制定是为了规范中国雅江集团有限公司（以下简称集团公司）元数据管理工作，结合数字雅江原生企业战略规划，落实数据互联互通互用和共建共治共享，实现源端治理，促进各业务域在数据开发和使用过程中提升规范性，更好地支持数据资源目录的构建和数据分析。本规范通过提供一套详细的、技术性的规则和指南，帮助集团公司有效地组织、整合和管理元数据，确保数据的准确性、一致性、可用性、可溯源性。
本文件起草单位：数信中心等单位。
本文件主要起草人：邵炜璇、xx等。


范围
本规范规定了对元数据管理技术实现的要求与约束。
本技术规范适用于集团公司各部门（包括总部部门、直属机构）、各单位（包括建设管理公司、专业公司）。

术语和定义、缩略语
术语和定义
元数据 Metadata
描述数据的数据，为数据提供上下文和解释，如数据的结构、来源、格式等。
元数据管理 Metadata Management
对元数据全生命周期进行规划、控制和优化的一系列活动。
元模型  Metadata Model
元模型是对元数据本身进行定义和描述的模型，是元数据管理的规则框架。元模型规范元数据的类型、属性、关系及约束条件，为元数据的采集、存储、应用等提供统一标准。
数据建模 Data Modeling
对现实世界中数据结构、关系及规则的抽象表示，以规范数据的结构、关系及业务规则的过程。
数据血缘 Data Lineage
描述数据从产生到最终应用的全链路流转过程，包括数据的来源、处理步骤和去向。
缩略语
下列缩略语适用于本文件。
CWM：公共仓库元模型（Common Warehouse Metamodel）
ETL: 抽取、转换、加载（Extract, Transform, Load）
XML：可扩展标记语言（eXtensible Markup Language）
JSON：JavaScript对象标记（JavaScript Object Notation）
TCP/IP：传输控制协议/网际协议（Transmission Control Protocol/Internet Protocol）
HTTPS：超文本传输安全协议（Hypertext Transfer Protocol Secure）
SFTP：安全文件传输协议（Secure File Transfer Protocol）
REST：表述性状态转移（Representational State Transfer）
SOAP：简单对象访问协议（Simple Object Access Protocol）
元数据管理技术框架
元数据管理模块的技术框架对内应具有良好扩展性，满足功能可复用、接口可开放。对外应提供方便的集成方式，其前端界面需集成到数据管理平台中。

具体模块应符合以下要求：
元数据来源应包括元数据存储库、业务术语表、数据资源表、数据建模工具、数据质量工具、商务智能工具、配置管理数据库等。
元数据采集模块支持提供一个可扩展框架，针对不同数据源配置特定的适配器，支持自动抽取与在线填报，以符合GB/T 30524-2014《科技平台 元数据注册与管理》的相关要求。
元数据存储应符合CWM规范，将元数据、元模型等信息统一存储在关系数据库中。
元数据质量管控对元数据完整性、一致性、及时性、准确性等提供评估与稽核能力。
元数据运维模块包括元数据变更、版本管理等。
元数据管理功能模块可提供服务调用集成到数据管理平台中，对外提供元数据浏览与查询等能力。
元模型
元数据来源识别
元数据来源识别应符合以下要求：
应识别业务涉及的所有元数据来源，数据源类型包括但不限于关系型数据库、非关系型数据库、数据仓库、数据湖、文件系统、线下文档等。
应明确数据源的识别层级，主要包括数据库级（库名、创建时间）、表级（表名、表描述）、字段级（字段名、数据类型、长度、约束条件）、流程级（ETL作业、数据链路）等。
应优先识别与业务强相关的元数据，主要包括业务规则、数据血缘、管理属性等。
元模型构建
元模型构建核心需要对元数据的实体、属性与实体关系进行定义，应符合以下要求：
应根据业务、技术、管理等需求来构建实体与属性，主要包括属性编码、中文名称、数据类型、取值规则等，可根据业务需求补充扩展属性。
应明确实体间的关联规则，主要包括包含、引用、血缘等，可尽量与具体业务贴近，以便于元数据的浏览与查询等业务应用。
元数据采集
元数据类型
元数据类型应涵盖元数据应用场景以及需要采集的元数据内容，可将元数据类型分为业务元数据、技术元数据、操作元数据。
业务元数据
业务元数据（Business Metadata）主要关注数据的内容和条件，另包括与数据治理相关的详细信息。业务元数据包括主题域、概念、实体、属性的非技术名称和定义、属性的数据类型和其他特征，如范围描述、计算公式、算法和业务规则、有效的域值及其定义。业务元数据包括：
数据集、表和字段的定义和描述。
业务规则、转换规则、计算公式和推导公式。
数据模型。
数据质量规则和检核结果。
数据的更新计划。
数据溯源和数据血缘。
数据标准。
特定的数据元素记录系统。
有效值约束。
利益相关方联系信息（如数据所有者、数据管理专员）。
数据的安全/隐私级别。
已知的数据问题。
数据使用说明。
技术元数据
技术元数据提供有关数据的技术细节、存储数据的系统以及在系统内和系统之间数据流转过程的信息。技术元数据包括：
物理数据库表名和字段名。
字段属性。
数据库对象的属性。
访问权限。
数据CRUD（增、删、改、查）规则。
物理数据模型，包括数据表名、键和索引。
记录数据模型与实物资产之间的关系。
ETL作业详细信息。
文件格式模式定义。
源到目标的映射文档。
数据血缘文档，包括上游和下游变更影响的信息。
程序和应用的名称和描述。
周期作业（内容更新）的调度计划和依赖。
恢复和备份规则。
数据访问的权限、组、角色。
操作元数据
操作元数据描述了处理和访问数据的细节，操作元数据包括：
批处理程序的作业执行日志。
抽取历史和结果。
调度异常处理。
审计、平衡、控制度量的结果。
错误日志。
报表和查询的访问模式、频率和执行时间。
补丁和版本的维护计划和执行情况，以及当前的补丁级别。
备份、保留、创建日期、灾备恢复预案。
服务水平协议（SLA）要求和规定。
容量和使用模式。
数据归档、保留规则和相关归档文件。
清洗标准。
数据共享规则和协议。
技术人员的角色、职责和联系信息。
 元数据采集方式
元数据采集应支持自动抽取、在线填报两种方式。
自动抽取
对于技术元数据，一般采用自动抽取方式，应符合以下要求：
应提供专门或者标准的元数据采集接口，如数据仓库和ETL工具，支持主流接口协议，以便自动实施元数据采集。
按照数据源类型和更新频率，应支持实时采集、定时采集、触发式采集。
应支持配置调度策略，支持时间周期触发和事件触发，以满足元数据采集在时效性和获取时机等方面的需要。
应支持增量采集，基于时间戳或日志序列号实现增量抽取，确保无重复、无遗漏，减少数据传输量。
当新数据源接入且未配置自动采集适配器或自动采集失败且无法通过重试机制修复等，应支持手动采集。
应支持元数据校验，对采集过程中的异常情况（包括连接失败、数据格式错误等）进行处理，应支持自动重试和告警机制。
在线填报
对于业务、操作元数据，一般采用在线填报的方式，应符合以下要求：
应提供界面进行元数据的在线填报。
应提供XML、JSON等格式的元数据导入模板，导入模板中规定元数据类型、标识符、名称、类型、来源等，并支持业务扩展字段。 
应支持元数据校验，包括必选字段完整性、格式规范性等，校验不通过的需标注异常字段并提示修改。
元数据传输
元数据采集传输协议应符合以下要求：
内部传输：局域网内采用TCP/IP协议，结合业务安全需要可配合加密通道传输。
跨网络传输：采用HTTPS或SFTP协议，禁止使用明文协议。
传输格式校验：元数据传输前需通过XML、JSON等验证格式合法性。
断点续传：对于大体积元数据，应支持断点续传机制，可通过分片传输与校验码比对确保完整性。
采集日志
元数据采集的日志应符合以下要求：
系统应记录采集全过程的操作日志，包括登录信息、采集行为、异常提示、提交记录等。
应记录每条传输记录的源地址、目标地址、时间、数据量、状态、错误码等，日志格式应符合GB/T 35275-2017《信息安全技术 大数据服务安全能力要求》中的相关要求。
应提供日志查阅和审计功能，支持按时间、人员等维度进行数据问题追溯。支持对异常信息提供告警功能，以符合GB/T 30881-2014《信息技术 元数据注册系统（MDR）模块》对告警响应的要求。
日志保存期限应大于等于5年，存放于不可篡改的日志服务器。
采集范围
元数据的采集范围应贯穿整个数据管理框架，共9个元数据数据管理对象：
数据标准：数据元标准有关的元数据集合，包括数据元的分类、定义、来源、规则、责任归属等。
逻辑模型：逻辑模型有关的元数据集合，包括实体、属性、关联规则、责任归属等。
数据资源目录：数据资源目录有关的元数据集合，范围覆盖集团公司各部门、各单位信息化系统的数据、主数据、数据管理平台的数据等，包括数据资源分类、数据表、属性、安全规则等。
数据共享目录：已入数据管理平台且可面向集团公司各部门、各单位共享的数据目录相关的元数据集合，包括目录层级、属性信息、安全规则等。
数据标签：数据标签有关的元数据集合，包括标签标识、标签分类、标签定义、实现逻辑、版本控制等。
指标数据：指标数据有关的元数据集合，包括指标名称、计算口径、更新频率等。
数据质量：数据质量有关的元数据集合，包括质量对象、规则类型、实现方式、责任归属等。
参考数据：参考数据有关的元数据集合，包括参考数据描述、数据来源、参考数据定义等。
物理模型：物理模型有关的元数据集合，包括数据库存储的物理表、属性、约束等。
在填报模板中已将冗余的管理对象进行合并，元数据管理对象的采集内容模板为《附件2元数据收集清单》详见附录A。数据标签及指标数据采集口径以《数据标签技术规范》、《指标数据技术规范》为准。
元数据存储
公司元数据库建设须以符合CWM标准为基础要求，结合公司元数据应用和管理要求进行元数据库建设。
元数据建库
元数据建库应符合以下要求：
应参考《数据仓库开发规范》进行开发，确保表和字段定义清晰、时间维度标准化、数据表结构和关系可追踪。
应将采集时间戳、编码参数、关联关系等存入数据库，以确保元数据关联关系和存放路径的合理性。
元数据存储方式
元数据存储应支持不同类别的元数据，为业务元数据、技术元数据、操作元数据建立存储分区，为各类型元数据提供适配存储结构，确保各类元数据有序存储且关系可追溯。元数据的存储方式应支持基于库表结构进行结构化元数据的存储。

访问接口
元数据库的访问接口应符合以下要求：
应在接口头信息中明确指定接口编码方式，包括UTF-8等，以保证数据的正确解析和显示。
应采用XML、JSON等接口响应格式，以支持数据的结构化表示和机器可读性。
应遵循的REST或SOAP的接口协议，确保不同系统间能够有效通信。
应预留跨领域扩展接口，以支持接入外部系统元数据，可通过标准化映射规则实现融合。
元数据变更
元数据变更要求
在满足元数据管理流程约束的情况下，元数据变更还应符合以下要求：
应支持根据变更评审后的需求进行更新，保持源端系统和元数据管理平台的一致性。
应支持定期审计，以保证元数据的准确性和时效性。
版本管理
版本管理应符合以下要求：
应支持发布控制，发布前应完成评估审核，主要包括版本内容、影响评估等。
应支持差异分析，主要包括元数据对象差异、属性差异等。
应记录历史版本信息，主要包括变更人、变更时间、变更内容等。
元数据质量管控
元数据质量管控应符合以下要求：
上线前，应通过元数据质量评估，主要包括元数据属性空值率、元数据关键属性值重复率、元数据更新延迟率、属性有效值率等，符合GB/T 32845-2016《科技平台 元数据汇交业务流程》中对元数据质量的要求。
上线后，应支持常态化质量稽核，以确保元数据满足完整性、一致性、及时性和准确性要求。
元数据退役
在满足元数据管理流程约束的情况下，元数据退役还应符合以下要求：​
（1）元数据退役时，应同步处理源端系统与数据管理平台的目标元数据，保持两端状态一致；元数据退役后，管理工具应及时获取情况并对应元数据进行归档，保障一致性。
（2）系统日志支持元数据退役全流程日志记录，确保退役过程可追溯。
元数据管理模块的功能要求
元数据展示
元数据展示应符合以下要求：
应将元数据转换为统一的格式进行展示，以可视化界面直观展示数据结构、关联关系与质量指标等，以符合GB/T 31073-2014《科技平台 服务核心元数据》的要求。
应支持展示必要的元数据元素，包括名称、关键字等必选元素，保证元数据的完整性。
元数据检索
元数据检索应符合以下要求：
应支持查询数据库表、维表、指标等基本信息。
应支持模糊、精确检索功能，可根据关键词、时间范围、数据类型等定位所需元数据。
数据资源目录
元数据的资源目录应符合以下要求：
应支持构建层级化、标准化的元数据目录，支持组织维度（部门/单位等）、主题域、属性等分类体系。
应包含资源必要字段，主要包括资源名称、责任人、创建时间等。
血缘分析
元数据的血缘分析应符合以下要求：
应支持可视化呈现，通过血缘追踪展示数据的全流程流转轨迹。
应支持解析表级、字段级的血缘分析，主要包括字段映射规则、表间关联关系、节点依赖关系等，以定位数据异常根源。
应确保血缘信息的时效性与完整性。
